# 11 · 产品功能设计

> 本文定义**产品长什么样**（功能清单、交互、优先级），与 01（架构）/03（语义层）/04（引擎）/05（安全）/10（创新点）配套。
> 技术侧的地基设计见前述文档，本文只写"用户能用到什么"以及"为什么必须这么设计"。

---

## 0. 定位与五条设计原则

**产品定义**：让医院管理者与临床科室，用自然语言问出**口径正确、可追溯、可解释**的聚合结果，并支持下钻、对比、归因与导出。

**本产品是只读产品**——这是它的第一性特征，不是限制：

| 只读原则 | 具体含义 |
|---|---|
| 对数据源零写 | 不写业务库、不写镜像库；抽取单向 |
| 不做患者级明细 | 默认关闭，需审批 + 审计才开（01 §1.2） |
| 不生成业务数据 | AI 不得补录、修复、推测任何业务事实 |
| 不改数字 | 质量差只标注，不修正（10 IN-03） |

**五条设计原则**（决定所有功能取舍）：

1. **口径优先于智能**：宁可反问、宁可说"我不会"，不可编造。错一个数字，信任归零且极难挽回（01 §1.3）。
2. **每个数字可追溯**：口径、SQL、快照、版本、数据截止时间，缺一不可。
3. **不可信必须显式标记**：未结算、质量低、源数据停更——系统只提示，绝不静默。
4. **物理映射配置化**：换一家医院只改配置，不动指标定义（见 §5.1）。
5. **拒绝也要完整**：越权、超范围、患者级，必须给出明确结论并留痕，**不能只回一句"暂不支持"**（04 §1 已定为硬约束）。

## 3. 核心交互流程（主链路）

```
用户提问
   │
   ├─(患者级围栏)────────────► denied：明确拒绝 + 留痕 + 告知审批路径
   ├─(越权预检)──────────────► denied：不反问、不泄露"这份数据存在"
   ├─(超范围)────────────────► out_of_scope：说明能力边界 + 建议替代问法
   ├─(命中歧义规则)──────────► need_clarify：卡片式反问 N1~N5
   │
   ▼
意图路由 → 指标召回 → 受限生成 DSL → 校验 → 生成 SQL → 执行
   │
   ├─(无数据 / 样本过小)─────► 上卷 或 明确"该细分不可用"
   ▼
结果卡片：数字 + 图表 + 口径条 + 成熟度 + 数据截止时间
   │
   ├─ 追问 / 下钻 / 对比  → 继承上文口径
   ├─ 切口径（F2.2）      → 结果同步刷新，口径条同步变化
   ├─ 查看 SQL / 快照     → 可追溯
   ├─ 导出                → 水印 + 审计
   └─ 反馈                → 回流 Golden 集
```

**状态机必须是五态**：`allow / need_clarify / denied / out_of_scope / no_data`。
不允许把 `denied` 降级成 `need_clarify`（04 §1 已由自测固化为硬约束）。

> **实现勘误（详见 [13 §3.3](13-界面产品化设计.md)）**：`engine/pipeline.py` 实际产出六个 status —
> `answered / meta / need_clarify / denied / out_of_scope / error`。其中 `allow` 对应 `answered`；
> `meta`（问口径）本文漏列；**`no_data` 在实现中不存在**，空结果仍回 `answered`（`rows` 为空），
> 界面需按 `answered && rows 为空` 判定，并区分"无数据行"与"有一行但值为 0"。

## 5. 由 HIS 实测反推出的设计要求

> 这一节是本文与通用 ChatBI 最大的区别——每一条都来自真实库的实测，不是想象。

### 5.1 物理映射必须配置化，不能硬编码

实测：业务散落 10+ schema（`MEDREC / OUTPBILL / INPBILL / EXAM / LAB / PHARMACY / ORDADM / HONLIVHP / REPORT`…），同一概念在不同院的表名完全不同。

设计：语义层拆成两层——
- **指标定义层**（与医院无关）：公式、口径参数、责任人、版本
- **物理映射层**（每院一套 adapter）：`指标 → schema.表.字段 / 关联键 / 过滤条件`

判定标准：**接入第二家医院时，如果动了指标定义层，就是设计失败。**

### 5.2 源数据域可能"半死"，产品必须能表达

实测：`DRG_DETAIL` 止于 2019-06；`REPORT.*` 整体止于 2024-10-06；`CLINIC_MASTER` 仅剩 348 行。
设计：每个数据源域都要有 `data_as_of`（数据截止时间）+ `freshness_state`（streaming / t_plus_1 / stale），
停更的域在指标上强制打 `source_stale` 角标，**不允许用户拿它当现状**。

### 5.3 源库统计信息不可信

实测：门诊费用估算 527 万、实测 4386 万（差 8 倍）。
设计：容量规划、预聚合策略、查询成本估算**一律基于自建 ADS 实测**，禁止读源库 `num_rows`。

### 5.4 口径对账工具（F5.7）是低成本高回报功能

实测：HIS 自带 `REPORT.RPT_DEPT_DAY`（科室 × 日 × 指标项，3040 万行，2019-01~2024-10）就是厂商自己的指标实现。

设计：用 2024-10 之前的历史数据，把我们算的「出院人次 / 平均住院日 / 次均费用」与它的 `ITEM_CODE` 逐项比对：

- 对得上 → 口径理解与医院现行报表一致，可以直接进 P1；
- 对不上 → **差异就是口径争议的证据**，拿着它去开 P0 口径确认会，比开会争论快得多。

### 5.5 脏数据必须进质量分，不能靠清洗"抹平"

实测：`1900-01-01`、`0001-01-01`、`4987-11-02`（出生日期）、`3015-01-31`（质控日期）、`VISIT_DATE` 空值率 43%。
设计：抽取层做**规则化清洗 + 计数留存**（清洗掉多少条要可查），剩余质量问题通过 F2.4 质量分暴露给用户，而不是静默丢弃后假装数据干净。

### 5.6 多数据源接入顺序

HIS 是首要数据源，但医院口径往往横跨多系统：

| 域 | 源 | MVP |
|---|---|---|
| 门诊/住院/费用/手术 | HIS | ✅ |
| 检验检查 | LIS / PACS | P2 |
| 病历文书 | EMR | P2 |
| 人力/物资/固定资产 | HRP | P3 |
| 财务总账 | 财务系统 | P3 |
| 医保结算 | 医保系统 | P2 |

### 5.6.1 多源「可配」的实现边界（v0.11）

**原则：多源接入在抽取层，不在查询层。** 问数引擎永远只面向**单一出数源**（`ASK_DS = ads | his`），
多源汇聚发生在抽取作业里（抽取 → ADS 宽表）。

为什么不让查询时同时连多个库——四条理由全部来自实测：

| # | 理由 | 实测依据 |
|---|---|---|
| 1 | 性能 | 直连 HIS 费用类 17.8~23.8 s vs ADS 52~68 ms（**343×**）；跨源 JOIN 只会更糟 |
| 2 | 权限 | 围栏是 SQL 层注入 `belong_dept_code IN (...)`，那是**宽表的列**；每个源都要重实现一遍 = 多份实现 = 多份漏洞 |
| 3 | 时效不同步 | `DRG_DETAIL` 停 2019-06、报表层停 2024-10、门诊滞后 29 天、病案归档滞后 3 个月。跨源 JOIN 两个时效不同的域，结果**无法向用户解释** |
| 4 | 方言 | 已为 Oracle 11g 单独写方言（`TO_CHAR`/`TO_DATE`/`ROWNUM`，修过 ORA-00911 / ORA-01861）；加一个源就加一套方言 |

**可配的三件事**（`app/config/sources.yaml`）：

1. **源登记**：每个源声明 `kind`（oracle / sqlite）、`layer`（`extract` 抽取来源 / `serve` 出数源）、
   `enabled`、`covers`。
2. **域归属**：`source_domains.yaml` 的每个域用 `source:` 声明属于哪个源（缺省 `his`，向后兼容），
   时效探测按源取连接器 —— 不再是写死 `his.query`。
3. **密钥只存环境变量名**：连接字段写 `password: ASK_LIS_PASSWORD`，**永不写明文、不允许默认值**。
   该约束由自测强制校验（`python -m app.core.sources --selftest`）。

**未接入的源必须显式表达**：`unconfigured` 与 `disabled` 是两个不同状态，
且 `missing` 会列出具体缺哪个环境变量 —— 「没接入」不能和「接入失败」都变成一句「跳过」。
时效取值因此扩展为 `streaming / t_plus_1 / delayed / stale / unconfigured / unknown`。

**已支持的源类型**：`oracle`（复用 `OracleSource` 只读守门）、`sqlite`（ADS 这类文件源）。
MySQL / PostgreSQL 等未实现，加的时候按 `sources.connector()` 工厂扩展即可。

**A 路线（ADS 宽表）的维度缺口（v0.15 实测）**：`scripts/build_ads.py` 只物化了
`discharge_dept_code / admit_dept_code`、日期三列、费用、床日、院内死亡、新生儿、`data_maturity`，
而语义层为住院域指标声明了 `campus / doctor / pay_type / discharge_type / stat_dept`。
除 `stat_dept`（院方 CASE 表达式算出来的分组）外，其余维度在 ADS 路线上**不可下钻/排名**。
界面已由服务端探测把这类维度标成"不可用 + 原因"（[docs/13 §7 C11](13-界面产品化设计.md)），
但要真正用上 F3 的分析能力，得在抽取作业里补齐这些列（或改走 HIS 路线 —— 那条路线
经 `physical_map_his.yaml` 映射到 `PAT_VISIT` 的真实列，维度是全的）。
