# 03 · 指标字典与语义层建模

> 语义层是本项目**唯一的核心资产**。模型可以换，指标定义不能散。

## 1. 指标分层

| 层级 | 定义 | 示例 | 数量占比 |
|---|---|---|---|
| **原子指标**（Measure） | 单一事实的直接聚合，不可再拆 | 门诊人次、出院人次、总费用、占用床日数 | 20% |
| **派生指标** | 原子指标 + 时间/维度/过滤条件 | 心内科上月出院人次、门诊次均费用 | 60% |
| **复合指标**（Ratio） | 两个及以上原子指标的运算 | 药占比、平均住院日、CMI、床位使用率 | 20% |

**只有复合指标允许写公式**，且公式必须由人工定义、代码评审后入库。

### 2.0 `sensitivity` 三级语义：取值必须配套可见性规则 ★

只定义取值、不定义每级的**可见性规则**，一定会出现「执行层按一个规则拦、
目录层按另一个规则藏」。实测中 `internal` 正是如此：执行层放行，目录层却要求额外授权，
导致 `科室主任` **能问出数、驾驶舱却是 0 个指标**（docs/12 §1.2 S9）。

因此三级语义与授权来源固定如下，**实现与文档都以本表为准**：

| sensitivity | 含义 | 可见性规则 | 授权来源 |
|---|---|---|---|
| `public` | 公开 | 所有角色可见 | — |
| `internal` | 院内 | **所有有效角色可见**，不需额外授权 | — |
| `restricted` | 受限（收入 / 药占比 / 死亡等） | 角色需在授权名单内 | **语义层 `permission.restricted_metrics_roles`（唯一事实来源）** |

两条硬性约定：

1. **授权名单只能有一份**：`restricted_metrics_roles` 由语义层持有，
   执行层（`engine/sql_builder.py`）与目录层（`app/core/permission.py`）都读它。
   `roles.yaml` 的 `sensitive_metrics` 仅在语义层未声明时作为回退，**不再作为主来源**。
   好处：改授权只需动语义层一处，两层同时生效。
2. **两层结论必须可断言**：任一 (角色, 指标) 上，`can_see_metric()` 的结论必须等于
   SQL 生成层的门禁结论。该断言已固化为回归：
   `python -m app.core.permission --selftest`（全角色 × 全指标对拍）。

### 2.2 必须写进 `notes` 的易错点（示例）

```yaml
ip_los_avg.notes: |
  分子必须是「出院者占用总床日数」，不是 SUM(出院日-入院日)。
  跨科转科患者按科室分摊床日；转科患者不计为新的一次出院。
drug_rate.notes: |
  本院口径：分子含西药+中成药，**不含中草药**；
  分母 = 医疗收入（不含其他收入、不含财政补助）；门诊+住院合并计算。
  与国家卫健委考核口径的差异：国家口径含中草药，导出报表时需单独出一份。
cmi.notes: |
  依赖 DRG 分组器版本（当前 CHS-DRG 1.1 / 本地细分组 v2.3），版本变更需重算历史。
```

## 3. 语义层选型对比

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **dbt + MetricFlow** | 与数仓建模一体、血缘天然、社区成熟、指标即代码 | 学习曲线；对中文支持一般；需 dbt 生态 | **推荐（标准方案）** |
| **Cube.dev** | 语义层独立、有缓存层、支持多后端、JS 生态友好 | 需额外部署 Cube 服务；与 dbt 有重叠 | 推荐（若不想绑 dbt） |
| **Apache Kylin** | 预计算强、亚秒级、国产 | 维度爆炸时成本高，建模灵活性弱 | 存量项目 |
| **自研轻量 YAML** | 完全可控、贴合中文与医疗口径、零学习成本 | 需自研查询生成器 | **推荐（MVP 冷启动）** |
| SuperSonic 内置语义层 | 自带问数引擎、中文友好 | 与自有体系整合成本 | 若采用 SuperSonic |

### 3.1 建议演进路径

```
MVP（8~12周）  自研轻量 YAML 语义层 + 自研查询生成器
      ↓  指标数 > 80、需要血缘与复用时
成长期        迁移至 dbt + MetricFlow（YAML 可脚本转换，schema 基本对齐）
      ↓  需要跨源、高 QPS 时
成熟期        MetricFlow + Cube 缓存层 / Kylin 预计算
```

> 关键：**自研 YAML 的 schema 设计要刻意对齐 MetricFlow**（measure / dimension / entity / metric / filter 概念一致），后期迁移成本极低。

## 4. 语义层 YAML 示例

### 4.1 自研轻量语义层（MVP 推荐）

完整可运行示例见 [`semantic-layer/metric_registry.yaml`](../semantic-layer/metric_registry.yaml)。

```yaml
version: "1.0"
domain: 住院运营

# ── 维度定义（可复用）────────────────────────────
dimensions:
  - code: dept
    name: 科室
    type: categorical
    table: dim_department
    expr: dept_code
    label_expr: dept_name
    alias: [科室, 临床科室, 病区, 部门]
    hierarchy: [campus, dept_group, dept]

  - code: stat_month
    name: 统计月份
    type: time
    granularity: [day, month, quarter, year]
    expr: stat_date

# ── 原子度量 ────────────────────────────────────
measures:
  - code: ip_discharge_cnt
    name: 出院人次
    table: dwd_fact_inpatient_discharge
    agg: count
    expr: visit_id
    date_basis:
      default: discharge
      supported: [admit, discharge, settle]
      expr_map:
        admit: admit_date
        discharge: discharge_date
        settle: settle_date
    dept_basis:
      default: discharge
      supported: [admit, discharge, belong]
      expr_map:
        admit: admit_dept_code
        discharge: discharge_dept_code
        belong: belong_dept_code
    dedup: visits          # visits | patients
    dedup_key: patient_id
    unit: 人次
    filters_inherit: true

  - code: ip_occupy_bed_days
    name: 出院者占用总床日数
    table: dwd_fact_inpatient_discharge
    agg: sum
    expr: occupy_bed_days
    date_basis:
      default: discharge
      supported: [discharge]
      expr_map: {discharge: discharge_date}
    dept_basis:
      default: discharge
      supported: [discharge, belong]
      expr_map: {discharge: discharge_dept_code, belong: belong_dept_code}
    unit: 床日

# ── 复合指标 ────────────────────────────────────
metrics:
  - code: ip_los_avg
    name: 平均住院日
    type: ratio
    unit: 天
    domain: 住院运营
    formula: "ip_occupy_bed_days / ip_discharge_cnt"
    numerator: ip_occupy_bed_days
    denominator: ip_discharge_cnt
    default_date_basis: discharge
    default_dept_basis: discharge
    agg_method: ratio          # ★ 禁止对自身做 avg 平均
    precision: 2
    alias: [平均住院日, 平均住院天数, 平均住院长度, ALOS]
    business_definition: 一定时期内出院者占用总床日数与出院人次之比
    notes: |
      分子必须是占用床日数，不是 SUM(出院日-入院日)。
      跨科转科按科室分摊床日。
    dimensions: [dept, campus, doctor, pay_type, discharge_type]
    owner: 医务处
    version: 1.0.0
    status: published
    sensitivity: internal
```

## 5. 查询 DSL（问数引擎的唯一输出格式）

LLM **只输出这个 DSL**，由语义层服务翻译成 SQL。这是受限生成的核心。

```json
{
  "intent": "query_metric",
  "metrics": ["ip_los_avg"],
  "dimensions": ["dept"],
  "filters": [
    {"field": "dept", "op": "=", "value": "心内科"},
    {"field": "pay_type", "op": "=", "value": "医保"}
  ],
  "time": {
    "granularity": "month",
    "range": {"type": "last_n_months", "n": 6},
    "date_basis": "discharge",
    "compare": {"type": "yoy"}
  },
  "options": {
    "dept_basis": "discharge",
    "dedup": "visits",
    "top_n": null,
    "order_by": {"metric": "ip_los_avg", "dir": "desc"}
  },
  "confidence": 0.93
}
```

**语义层服务 → SQL 的生成规则**（伪代码）：

```python
def build_sql(dsl: dict, user_ctx: PermissionContext) -> str:
    metric = registry.get(dsl["metrics"][0])
    # 1. 解析 metric → 底层 measure 与公式
    # 2. 选择 date_basis 对应的日期字段
    date_col = metric.date_basis.expr_map[dsl["time"]["date_basis"]]
    dept_col = metric.dept_basis.expr_map[dsl["options"]["dept_basis"]]
    # 3. 按 ratio / atomic 生成不同 SQL
    #    ratio  → SUM(num)/SUM(den)  ★ 先聚合再相除
    #    atomic → AGG(expr)
    # 4. 注入行级权限过滤（用户可见科室/院区）
    sql = apply_rls(sql, user_ctx)
    # 5. 注入脱敏规则
    return apply_masking(sql, user_ctx)
```

> **`ratio` 类型的关键**：必须先分别聚合分子分母，再相除。绝不能先算每行比率再平均（经典错误：平均住院日的平均值 ≠ 总体平均住院日）。

## 6. 歧义词表（触发反问）

维护方式：`semantic-layer/ambiguity_rules.yaml`（v1.1），支持热更新。

> ⚠️ **v1.1 方向性修正**：原表述「出现触发词**即**反问」是错的。实测反问率接近 50%，
> 表达明确的问句（"各科室平均住院日排名前10"）也被反问，产品不可用。
> 现在的规则是 **N1~N5 全部满足才反问**，且有 R1~R3 三条硬否决，
> 详见 [04 §3.1](04-问数引擎设计.md#31-触发条件v11全部满足才反问)。

| ID | 触发（命中才考虑反问） | 歧义点 | **已消歧标记**（命中即不问） | 模式 |
|---|---|---|---|---|
| AMB-001 | 门诊量 / 门诊人数 / 门急诊量 | 人次 vs 人数；挂号 vs 有效就诊 | 有效就诊、挂号人次、**门诊人次**、去重人数 | ask |
| AMB-002 | 收入 / 营收 / 毛收入 | 门诊/住院/全院；是否含药品 | **门诊收入、住院收入、医疗收入**、含/不含药品 | ask |
| AMB-003 | 药占比 / 药品占比 | 是否含中草药 | 院内口径、国家考核口径、含/不含中草药 | ask |
| AMB-004 | **问题中点名具体科室**（registry 科室枚举） | 开单 / 执行 / 患者归属 | 开单科室、执行科室、患者归属、出院科室 | ask |
| AMB-005 | 住院收入 / 住院费用 / 医疗收入 | 出院日 vs 结算日 | 按结算、按出院、按入院 | **echo_only** |
| AMB-006 | 自然月 / 财务月 / 会计月 | 自然月 vs 医院财务月 | 按自然月、按财务月 | ask |
| AMB-007 | 手术量 / 手术例数 / 手术台次 | 主手术 vs 全部操作；是否含介入 | 主手术、含介入、**四级手术** | ask |
| AMB-008 | 床位使用率 / 病床使用 | 实际开放 vs 编制床位 | 实际开放床位、编制床位 | ask |
| AMB-009 | 死亡率 / 病死率 / 死亡 | 院内死亡 vs 含随访死亡 | 院内死亡、住院期间死亡 | ask |
| AMB-010 | 再入院 / 重返 | 计划性 vs 非计划；窗口 | **31天 / 15日 / 7日、非计划** | ask |
| AMB-011 | 排名 / 排第几 / 排序 | 升序降序、Top N | **最高、最低、前10、前20、Top** | ask |
| AMB-012 | 最近 / 近期 / 一段时间 | 窗口未定义 | 近半年、近三年、本月、上个月 | ask |
| AMB-013 | 增长 / 涨了 / 涨幅（**不含**"同比"） | 对比基准 | **同比、环比、与去年**；DSL `compare` 已指定 | ask |
| AMB-014 | 多少人 / 多少患者 / 患者数 | 人次 vs 人数 | 人次、人数、去重 | ask |

**两条被推翻的旧设计（保留在此，避免重犯）**：

- ~~「科室」裸词触发归属反问~~ → 「各科室排名」的「各科室」是**分组维度**不是归属口径，
  裸词会让几乎所有分科室查询都被反问；同时真正的归属歧义（"神经外科平均住院日"）反而漏问。
  改为按 registry 科室枚举判定「是否点名科室」，并用 `supported_min: {dept_basis: 2}`
  过滤掉只有一个可选口径的指标（如四级手术只支持 exec）。
- ~~「同比/环比」「上月/本月」当触发词~~ → 它们本身就是最明确的消歧表达，
  反问等于对用户已知信息提问（对应 [04 §3.2](04-问数引擎设计.md)「不要反问已知信息」）。

### 6.1 口径写回（apply）：选项选完，DSL 到底怎么变（v1.2 新增）

反问只解决"问清楚"，**问清楚之后必须真的改到 DSL 上**。
`apply` 段把「选项文本 → DSL 取值」声明在**语义层**（不写进代码，同 ADR-03）：
口径是院方的资产，不该变成工程师的知识。

```yaml
  - id: AMB-011
    options: [最高前10, 最低前10, 全部排序]
    apply:
      set:                                       # ② 一次改多处
        最低前10:
          options.order_by: {metric: "@metric", dir: asc}
          options.top_n: 10
        全部排序:
          options.order_by: {metric: "@metric", dir: desc}

  - id: AMB-012
    apply:
      field: time.range                          # ① 单选字段
      range_type: last_n_months
      values: {最近3个月: 3, 最近6个月: 6, 最近12个月: 12}

  - id: AMB-009
    apply:
      alias_to_default: [住院期间死亡, 院内死亡]   # ④ 等同本院默认口径
      unresolvable_values:
        含出院后死亡: 随访死亡不在 HIS 数据范围内   # ③ 做不到，必须说清原因
```

| 写法 | 用途 |
|---|---|
| `field` + `values` | 一个选项改一个 DSL 位置（可配 `range_type` 生成 `{type,n}`） |
| `set` | 一个选项同时改多处（排序方向 + Top N） |
| `alias_to_default` | **逐条列出**院方认可的同义说法（"这些说法在本院就是默认口径"）。不是模糊匹配：没列的按下面处理 |
| `unresolvable_values` / `unresolvable` | 做不到的选项 / 整条规则，**必须写原因**，管线据此拒绝出数 |

**两条红线**：

1. **未声明映射的选项不会被静默忽略**：管线拒绝出数并说明原因
   （"选了当没选、按别的口径给数"是比反问更坏的结果 —— docs/11 §1）。
2. **映射必须与指标的 `supported` 相容**：写回后管线会再跑一次 `validate_dsl`，
   不兼容（如给门诊指标选了「出院日期」）则整批回退。自测里有静态检查兜底，
   路径非法 / 取值不在枚举 / 指标未注册 / 选项未分类，一律 FAIL。

**14 条规则的口径写回现状**（自测会守住这张表）：

| 规则 | 形态 | 说明 |
|---|---|---|
| AMB-001 | `metrics` | 有效就诊人次→`op_visit_cnt`；去重人数→`op_patient_cnt`；**挂号人次未声明**（本院无该指标） |
| AMB-002 | `metrics` | 仅门诊→`op_revenue`；仅住院→`ip_revenue`；**全院医疗收入未声明**（需两个指标，本版本只取 `metrics[0]`） |
| AMB-003 | 等同默认 + 做不到 | 院内口径=默认；国家考核口径（含中草药）无指标实现 |
| AMB-004 | `options.dept_basis` | 归属→`belong`／开单→`order`／执行→`exec`；另声明 出院科室→`discharge`、入院科室→`admit` 以兼容口语与 Golden 措辞 |
| AMB-005 | `time.date_basis` | 出院→`discharge`／入院→`admit`／结算→`settle`（echo_only，不反问） |
| AMB-006 | 等同默认 + 做不到 | 自然月=默认；财务月由院级配置决定，问数时不可切换 |
| AMB-007 | 等同默认 + 做不到 | 全部手术操作/含介入=默认（`surgery_cnt`）；仅主手术无字段区分 |
| AMB-008 | 等同默认 + 做不到 | 实际开放床位=默认；编制床位无对应度量 |
| AMB-009 | 等同默认 + 做不到 | 住院期间死亡=默认；含出院后死亡不在 HIS |
| AMB-010 | `metrics` | 31日非计划→`unplanned_readmit_31d_rate`；15/7 日窗口未注册 |
| AMB-011 | `set` | 最高/最低前10、全部排序 → `order_by` + `top_n` |
| AMB-012 | `time.range` | 3/6/12 个月 → `last_n_months` |
| AMB-013 | `time.compare` | 同比→`yoy`／环比→`mom`；「两者都要」DSL 表达不了 |
| AMB-014 | `options.dedup` | 人次→`visits`／人数→`patients` |

## 7. 指标变更管理流程

```
 业务提出变更（口径调整/新增指标）
        │
        ▼
 填写《指标定义单》（含公式、口径、责任人、生效日期）
        │
        ▼
 业务责任人（医务/财务/医保）确认  ← 必须有"谁说了算"的人签字
        │
        ▼
 数据团队实现（改 YAML + 改 dbt model）
        │
        ▼
 代码评审（MR，至少 1 人 review）
        │
        ▼
 回归测试：跑 Golden 集，确认历史指标值无意外漂移
        │
        ▼
 灰度：先在"测试指标"标签下开放，业务核对 3 天
        │
        ▼
 发布：version +1，记录 changelog，通知全部订阅用户
        │
        ▼
 回溯：若影响历史数据，重跑 ADS 并标记 restated
```

**红线**：禁止直接改生产语义层 YAML 而不走评审。指标口径的信任一旦崩塌，产品即死。

## 8. 语义层 checklist

- [ ] 每个指标都有唯一的 `metric_code` 和业务责任人
- [ ] 所有 ratio 指标显式声明分子/分母指标编码
- [ ] 所有指标显式声明 `default_date_basis` / `dept_basis` / `dedup`
- [ ] 每个指标配置 `alias`（≥3 个通俗别名），用于问数召回
- [ ] `business_definition` 用人话写，会直接用于前端 tooltip 和 LLM 上下文
- [ ] ratio 指标禁止跨时间 `avg` 平均（只能 sum(num)/sum(den)）
- [ ] 版本化 + changelog
- [ ] 指标下线走 deprecated 而非直接删除
