# 10 · 创新设计与可行性评估

> **原则**：创新只对"已经算得对"的部分做加法。
> 本清单中的每一项都必须回答三个问题：**解决什么真问题**、**凭什么不会算错**、**多大代价**。
> 凡无法回答第二条的，一律列入「明确不做」。

## 判定图例

| 标记 | 含义 |
|---|---|
| 🟢 **MVP 即做** | 工程量小、无准确率风险、直接提升可用性 |
| 🟡 **P2 试点** | 有差异化价值，需先在 1 个科室验证再推广 |
| 🔵 **P3 探索** | 依赖前置能力，风险较高 |
| ⛔ **明确不做** | 噱头 / 合规风险 / 会损害信任 |

# Tier 1 · MVP 即做（低风险、高价值）

## IN-01 口径卡片与偏好记忆（Caliber Card）

**真问题**：反问会打断体验；同一用户每次都被问同样的口径问题。

**方案**
不弹纯文本反问，而是渲染一张**口径卡片**，随每次回答常驻：

```
┌─ 平均住院日 · 8.42 天 ─────────────────────────┐
│ [时间口径: 出院日期 ▾] [科室: 出院科室 ▾]      │
│ [统计: 人次 ▾]        [含: 全院]               │
│ 📌 有效就诊口径不含退号 · 数据已结算            │
│                          [记住我的选择]        │
└────────────────────────────────────────────────┘
```

- 每个 chip 的可选项直接来自语义层的 `supported` 列表，**UI 不得凭空造口径**
- 用户选择后写入 `user_caliber_profile`，后续默认沿用
- **但每次回答仍回显当前口径**（防止用户忘记自己改过）

**严谨性**
- 偏好只影响 `default`，不影响 `supported` —— 用户偏好无权突破语义层约束
- 偏好按 (用户, 指标域) 存储，不跨域扩散（住院口径偏好不应影响门诊）
- 切换口径时结果必然变化，卡片会同步刷新，不会出现"数字变了但口径没变"

**可行性**：前端组件 + 1 张偏好表，**1~2 人周**，无算法风险。🟢

## IN-02 数据成熟度分层渲染（Data Maturity Layering）

**真问题**：本月数据未结算，趋势图尾部"虚假下跌"，被院长误读为业务下滑，做出错误决策。这是医院 BI 最常见、后果最严重的误读。

**方案**
语义层为每个结果单元打标记，前端三层渲染：

| maturity | 触发条件 | 前端表现 | 说明文案 |
|---|---|---|---|
| `settled` | 数据已结算落定 | 实线、黑色 | — |
| `provisional` | 未结算 / 周期未结束 | 灰色虚线 + 角标 | "未结算，数值可能变化" |
| `restated` | 已被回刷修正 | 橙色 + 可对比 | "本数据已修正，查看原值" |

判定规则写进语义层而非前端：
- 财务类指标设**结算截止日**（如次月 5 日），在此之前一律 `provisional`
- 月末统计的"31 日再入院率"窗口未走完 → 自动 `provisional`
- 回刷后 `etl_time` 变化的分区 → 标记 `restated` 并保留原值快照

**严谨性**
- maturity 来自 ADS 表字段，不是估算
- 是**提示**不是**修正** —— 系统从不改数字，只标注可信度
- `restated` 必须保留原值，用户可对比，不允许静默覆盖

**可行性**：数据层加字段 + 前端渲染规则，**0.5~1 人周**。**本清单中性价比最高的一项**——投入极小，直接避免最严重的一类误读。🟢

## IN-03 上游质量驱动的指标置信度（Quality-Propagated Confidence）

**真问题**：某科室 ICD 映射失败率 20%，但问数照样给出一个精确到小数点后两位的值，用户无从判断能不能用。

**方案**
给每个 (指标, 科室, 时间) 单元算质量分：

```
Q = 0.3·映射覆盖率 + 0.25·字段完整性 + 0.2·数据及时性 + 0.25·源系统对账一致率
```

最终置信度 = 模型置信度 × Q。分档处理：

| Q | 行为 |
|---|---|
| ≥ 0.95 | 正常展示 |
| 0.80 ~ 0.95 | 展示 + 可展开的质量提示 |
| < 0.80 | **强制附加质量告警**，并列出缺失项；仍展示数值，由用户判断 |

**严谨性**
- Q 只做**降级提示**，绝不修正数值（修正等于伪造）
- 权重与规则写进质量规则库并版本化，不是拍脑袋
- Q **本身可查询**："为什么这个数不可信" → 展开四个分项与缺失明细
- Q 不参与任何考核口径，只用于提示

**可行性**：Great Expectations 结果落表 + 加权计算，**1~2 人周**。依赖质量规则先建立（P1 阶段）。🟢

## IN-06 口径快照与可回溯（Caliber Snapshot）

**真问题**：评审/考核场景，三个月前汇报的数字现在对不上了，说不清是口径变了还是数据回刷了。这类"说不清"在医院会造成真实的责任纠纷。

**方案**
每次查询结果落一张**不可变快照**：

```
snapshot = {
  答案ID, 问题原文, 指标版本, 口径参数(date_basis/dept_basis/dedup),
  生成的SQL, 结果hash, 数据版本(etl_time), 指标定义快照, 时间戳
}
```

任何历史答案可一键：
1. **复现**（用当时的口径 + 当时的数据版本重跑）
2. **差异说明**（口径变了？数据回刷了？指标定义改了？—— 只做事实陈述）

**严谨性**
- 快照 append-only，不可篡改
- 差异说明只陈述事实（"指标定义 v1.0→v1.1，药占比分子改为含中草药"），**不做责任判断**
- 指标定义随快照保存副本，即使指标被下线也能回溯

**可行性**：1 张表 + 1 个对比服务，**1 人周**。医院评审/考核刚需，商业价值高。🟢

## IN-08 LLM 解读的数字护城河（Number Guardrail）

**真问题**：让 LLM 写"同比下降 3.5%，主要因为心内科…"，它会顺手编一个数字。这是问数产品最致命的信任杀手。

**方案**：三层硬校验（**不是提示词约束，是代码校验**）

```
第 1 层 槽位填充：数字全部由系统模板注入，LLM 只组织语言
第 2 层 集合校验：正则抽取 LLM 输出中的所有数字，
                 必须与「授权数字集合」完全一致；
                 出现任何未授权数字 → 丢弃本次生成并重试（≤2 次）
第 3 层 断言过滤：禁止因果词（"导致""因为""由于"），
                 除非有 IN-04 的结构-价格分解作为支撑
```

**严谨性**
- 数字比对是**集合相等**判定，不是相似度 —— 多一个数字也拒绝
- 重试仍失败 → 降级为纯表格 + 模板化结论，**绝不裸奔 LLM 输出**
- 因果词过滤用词典 + 依存规则，误伤率可控（宁可少说，不可乱说）

**可行性**：**1 人周，必须与 IN-07 主动问数同时上线**。🟢

# Tier 2 · P2 试点（差异化价值）

## IN-04 结构-价格两因素归因（Shift-Share 分解）★ 最推荐

**真问题**："住院次均费用涨了 8%"——是乱收费？还是病例变难了？现有 BI 只会说"某科室涨最多"，无法区分。而这两种情况的管理动作完全相反。

**方案**：对次均费用做**恒等式分解**（不是回归，不是因果推断）

设病例组 `g`（DRG 组 / 科室），`w_g` = 该组出院人次占比（Σw=1），`p_g` = 该组次均费用。基期 `0`，报告期 `1`：

```
ΔP = P₁ − P₀ = Σw₁p₁ − Σw₀p₀

   = Σ(w_g1 − w_g0)·p_g0          ← 结构效应（病例构成变化，按基期价格计价）
   + Σ w_g0 ·(p_g1 − p_g0)        ← 价格效应（各组费用水平变化，按基期结构加权）
   + Σ(w_g1 − w_g0)(p_g1 − p_g0)  ← 交互项（结构与价格同时变化）
```

输出示例：

> 次均费用同比 +8.2%
> · 结构效应 **+6.1 pt**（74%）—— CMI 由 1.12 升至 1.21，四级手术占比 +3.2pt
> · 价格效应 **+1.5 pt**（18%）
> · 交互项 **+0.6 pt**（7%）
> 结论方向：费用上升主要由**病例结构变难**驱动，非单价上涨。

**严谨性论证**
1. 这是**代数恒等式**（展开后恰好抵消为 P₁−P₀），不含任何模型假设 → 不会给出错误的分解
2. 交互项**必须单列**，禁止并入任一主效应（这是 shift-share 分解最常见的错误）
3. 前置门禁：**DRG 分组器版本跨期必须一致**，否则基期需按新版重算，分解无意义
4. 结构效应须用 CMI / 四级手术占比做**交叉验证**；两者方向矛盾时标注"分解需复核"
5. `|交互项| / |ΔP| > 20%` 时，明确提示"结构与价格同时变化，分解解释力有限"
6. **只做分解，不做因果断言** —— 输出"由…驱动"，绝不输出"因为…导致"

**可行性**：纯 SQL / DataFrame 可实现，**1~2 人周**；依赖 DRG 分组稳定（分组器升级月份需跳过）。🟡 先在 1 个重点科室试点。

### 参考实现（已完成，自测 15/15 通过）

```
engine/attribution.py      分解器 + 恒等式自测 + SQL 生成
eval/golden_attribution.jsonl   7 条归因用例（含 4 条门禁反例）
```

```
python engine/attribution.py --selftest
```

数学形式扩展为**五项**（存在组别增减时仍为恒等式）：

```
ΔP = a0·(结构_C + 价格_C + 交互_C) + 新增组效应 + 退出组效应
```

`a0` 为共同组在基期的例数占比，`_C` 表示只在两期共同存在的组内计算。
无组别增减时 `a0=1`、后两项为 0，自动退化为标准三项分解。

自测覆盖：随机 20 组的恒等式、纯结构/纯价格的零效应、组别增减、以及 G1~G5 五道门禁的反例。

> **实现过程中真实抓到的两个问题**（记录在此，因为它们同类问题会反复出现）：
> 1. 自测第 8 项一开始失败，排查后发现是**测试数据设计错了**——让低费用组占比上升，结构效应为负，与 CMI 上升本就矛盾。是数据错不是代码错。
> 2. 解读模板把「水平变化」写死为「费用水平」，用于**平均住院日**时输出了"科室内费用水平变化"——错误表述。已改为 `level_name` 参数强制传入（费用 / 住院日 / 例均）。

## IN-05 口径漂移哨兵（Metric Drift Sentinel）★ 医疗特色

**真问题**：DRG 分组器升级、ICD 版本切换、科室合并、HIS 接口改造 → 指标值突变。没人知道是"业务真的变了"还是"数据管道变了"。CMI 一夜之间跳 0.15，全科室以为是业绩提升。

**方案**：三层监控 + 证据链

```
① 变点检测：对指标残差序列跑 CUSUM
     S_t = max(0, S_{t−1} + (r_t − k))，S_t > h 触发
   （资源允许时用 BOCPD 贝叶斯在线变点，给出后验概率）

② 事件对齐：变点时刻 ±3 天内检索「变更事件流」
     {DRG分组器版本, ICD字典版本, ETL版本, 科室变更, HIS接口变更}
     命中 → 标 suspected_data_artifact，附事件 ID 与时间差

③ 交叉验证：用不受该变更影响的同源指标做对照
     CMI 突变但出院人次平稳、费用结构平稳 → 大概率分组器问题
```

输出**三分类**，不允许二分类：

| 分类 | 判据 | 处理 |
|---|---|---|
| `data_artifact` | 命中变更事件 + 交叉验证一致 | 强提示"疑似数据变更，非业务变化" |
| `business_change` | 无变更事件 + 交叉验证支持 | 正常 |
| `unknown` | 证据不足 | **只提示"存在变点"，不做任何归因** |

**严谨性**
- **只标记、不修正** —— 系统绝不自动"修正"历史值
- 每条告警必须附**证据链**（变更事件 ID + 时间差 + 对照指标），无证据不告警
- 召回优先于精确：宁可多标几个让用户确认，不可漏标
- `unknown` 是合法输出，不允许为了"看起来聪明"强行归因

**可行性**：**2~3 人周**；前置工作是先把「变更事件流」做成结构化日志（这件事本身就有价值，建议 P1 就做）。🟡

# Tier 3 · P3 探索

## IN-07 主动问数（Proactive Insight）

**真问题**：从"人问"到"机器说"，是问数产品价值跃迁的关键一步。

**方案**：异常检测 → 归因 → 推送到责任人 → 反馈闭环

**严谨性风险（必须正视）**
- 误报疲劳：管理者被无关告警淹没后，会整体忽略推送
- 归因错误：一次错误的"为什么"会摧毁长期建立的信任

**降风险设计**
1. **第一阶段只推异常检测，不推归因**（归因留给 IN-04 成熟后）
2. 阈值保守：只对 3σ 以上偏离告警
3. 每条推送带一键反馈「有用 / 误报」
4. **误报率 > 30% 自动降频**，> 50% 自动下线该指标推送
5. 推送内容必须可点进完整问数会话，不允许"只给结论不给依据"

**可行性**：依赖 IN-04/IN-05 与稳定调度。🔵

## IN-09 小样本保护：不做差分隐私，做自适应层级上卷

**真问题**：k<5 抑制会导致大量单元格不可用，科室主任下钻到自己科室的罕见病时什么都看不到，体验很差。

**被否决方案**：加校准噪声（Laplace 机制）
- ❌ 管理者需要**精确数字**做考核，加噪声会让"我用你的系统报的数"失去效力
- ❌ 医院用户对"数字被改过"零容忍

**采纳方案**：**自适应层级上卷**

```
查询：心内科 × 罕见病 × 2026-09  → 3 例（< 5）
   ↓ 自动上卷
展示：心内科 × 罕见病 × 2026 全年  → 17 例  ✅
提示："该细分样本量不足（3 < 5），已自动上卷至年度，原细分不展示"
```

**严谨性**
- 上卷路径由维度层级预先定义（科室→科室组→全院；月→季→年），不是随意聚合
- 原细分值**完全不返回**（连"3"都不显示，因为 3 本身已接近可识别）
- 上卷行为明确告知，用户知道看到的是什么

**可行性**：0.5 人周，可并入 MVP。🟢（**替代方案，不是 IN-09 的原始设想**）

# 明确不做（附理由）

| 设想 | 不做的理由 |
|---|---|
| **用 LLM 自动写指标定义 / 自动推导公式** | 指标口径是**人工资产**，必须评审留痕。让模型生成口径 = 把正确性交给概率 |
| **预测类问数**（"下月门诊量多少"） | MVP 阶段预测误差会反噬信任。用户会记住"它说会涨结果跌了"，而不会记住 9 次说对。留到 P3 且必须与实测并列展示 |
| **全自动科研队列构建** | 合规风险高，且 OHDSI ATLAS 已解决。不重复造轮子 |
| **语音问数 / 多模态** | 医院办公场景价值低，投入产出比差 |
| **用大模型做数据补录与修复** | 合规禁止。数据只能来自源系统，AI 不得生成业务数据 |
| **跨院对标基准** | 需要院外数据，涉及数据出域，合规路径不通。若院方有上级平台授权可另行评估 |
| **让 LLM 直接生成 SQL 走"自由探索"** | 已在 [01 §5](01-架构总体方案.md#5-三条技术路线决策关键) 否决为生产路线。仅保留给数据分析师的只读沙箱，且结果强制标注"未经验证" |

# 与工程实现的对应关系

本清单中的创新点均**不依赖模型能力**，全部落在已工程化的地基上：

| 创新点 | 依赖的地基 |
|---|---|
| IN-01 口径卡片 | `semantic-layer/metric_registry.yaml` 的 `supported` 列表 |
| IN-02 数据成熟度 | `engine/sql_builder.py` 的 `data_maturity` 过滤 + `warnings` 输出 |
| IN-03 质量置信度 | Great Expectations 规则库（[02 §8](02-数据模型设计.md#8-数据质量规则great-expectations-建议内置)） |
| IN-04 结构-价格分解 | 语义层的 DRG 权重与费用度量（`drg_weight_sum` / `ip_avg_fee`） |
| IN-06 口径快照 | `sql_builder.build()` 返回的 `caliber`（含指标版本、公式、口径） |
