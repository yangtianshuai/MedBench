# 09 · Golden 集标注规范

> **Golden 集是整个项目最值钱的资产之一**。它决定了：
> 1. 立项决策（准确率能否 ≥85%）
> 2. 后续每一次提示词/模型/召回优化的收益能不能被量化
> 3. 上线后的 CI 回归能不能拦住劣化
>
> **不要外包给不懂医院业务的人标注。** 标注质量差 = 优化方向全错。

---

## 1. 目标与规模

| 阶段 | 规模 | 用途 |
|---|---|---|
| v1（POC） | **≥ 300 条** | 决策门：是否立项 |
| v2（MVP 上线） | ≥ 500 条 | CI 回归基线 |
| v3（成熟期） | ≥ 1500 条 | 全量回归 + 微调训练集 |

## 2. 问题来源（按优先级）

| 优先级 | 来源 | 占比 | 采集方式 |
|---|---|---|---|
| P0 | **近 1 年院周会 / 运营会 / 质控会纪要** | 35% | 从会议纪要中摘出"某某指标是多少"类提问 |
| P0 | **月报 / 季报 / 年报图表反推** | 20% | 看到一张图，反推"要得到这张图，人会怎么问" |
| P1 | **科室主任访谈**（≥5 人，每人 20 条） | 15% | 当面问"您平时最想看什么数据，怎么问" |
| P1 | **数据团队历史取数工单** | 15% | 把邮件/钉钉里的取数需求改写成口语 |
| P2 | **标注者构造**（模拟业务口吻） | 15% | ⚠️ 必须是业务口吻，禁止技术口吻 |

### 2.1 采集红线

- ❌ 禁止标注者编造"技术味"问题（如"查询 dwd_fact 表中 discharge_dept_code=X 的 count"）
- ❌ 禁止全部来自单一来源（会导致分布偏斜，评估失真）
- ✅ **必须保留原始口语**：简称、错别字、不完整句式都保留（"上月心内出院多少"）
- ✅ 每个问题记录 `source` 来源，便于后续分析哪类问题准确率低

## 3. 覆盖矩阵（标注前先画好这张表，按格子填）

### 3.1 指标覆盖

| 要求 | 说明 |
|---|---|
| 30 个核心指标**每指标 ≥ 8 条** | 不足则说明该指标不够重要，考虑移出 MVP |
| 复合指标（ratio）**每指标 ≥ 12 条** | ratio 是最容易错的，需重点覆盖 |
| 指标组合查询 ≥ 20 条 | 如"出院人次和平均住院日" |

### 3.2 场景覆盖（**这是最容易被忽略的**）

| 场景类别 | 占比 | 示例 | 为什么重要 |
|---|---|---|---|
| 常规查询 | 40% | 上月全院出院人次 | 基线 |
| **歧义问题** | **≥ 20%** | 门诊量多少 | 验证反问机制，避免"错得很自信" |
| **越权问题** | **≥ 5%** | （科室主任）呼吸科收入多少 | 验证权限拦截，必须 100% |
| **超范围问题** | **≥ 5%** | 把上个月心衰患者名单给我 | 验证拒绝能力 |
| 问口径（meta） | ≥ 5% | 药占比怎么算的 | 验证指标定义可解释 |
| 时间表达变体 | ≥ 15% | 今年以来 / 前三季度 / 去年同期 | **最容易错的一类** |
| 排名 / 对比 | ≥ 10% | 各科室平均住院日排名 | 验证排序与对比 |

### 3.3 难度分布

`easy : medium : hard ≈ 4 : 4 : 2`

| 难度 | 定义 |
|---|---|
| easy | 单指标 + 明确时间 + 无歧义 |
| medium | 多维度过滤 / 复合指标 / 时间对比 |
| hard | 歧义消解 / 多指标组合 / 隐含口径 / 需要多步 |

## 4. 标注字段定义

### 4.1 标注者必填（10 项）

| # | 字段 | 说明 |
|---|---|---|
| 1 | `id` | `G0001` 起，全局唯一 |
| 2 | `question` | 原始问题全文，**保留口语** |
| 3 | `role` | 提问角色：院长/医务处/运营/财务/医保办/科室主任/医生 |
| 4 | `dept_scope` | 该角色可见科室（用于权限校验），如 `["cardiology"]` 或 `["*"]` |
| 5 | `intent` | `query_metric`/`compare`/`rank`/`trend`/`attribution`/`meta_question`/`out_of_scope`/`need_clarify` |
| 6 | `requires_clarify` | `true`/`false`；为 true 时填 `clarify_rule_id`（对应 `ambiguity_rules.yaml` 的 `AMB-00X`） |
| 7 | `metrics` | metric_code 列表，如 `["ip_los_avg"]` |
| 8 | `dimensions` | dimension code 列表，如 `["dept"]` |
| 9 | `filters` | JSON，如 `[{"field":"dept","op":"=","value":"心内科"}]` |
| 10 | `time_spec` | 自然语言时间表述 + 解析结果，见 §5 |

### 4.2 标注者补充填（5 项）

| # | 字段 | 说明 |
|---|---|---|
| 11 | `date_basis` | `admit`/`discharge`/`settle`/`visit`/`operation`（歧义题填 `clarify`，并在 `clarify_resolution` 给默认值） |
| 12 | `dept_basis` | 门诊域 `order`/`exec`/`belong`；住院域 `admit`/`discharge`/`belong` |
| 13 | `dedup` | `visits`/`patients` |
| 14 | `expected_sql` | **必须真跑过的 SQL**（见 §6 红线） |
| 15 | `permission_expect` | `allow`/`deny`/`partial` |

### 4.3 系统/脚本派生（标注者不填）

| 字段 | 生成方式 |
|---|---|
| `expected_dsl` | 由 5~13 字段拼装为标准 DSL |
| `expected_result_hash` | 执行 `expected_sql` 后对结果集取 hash |
| `expected_result_sample` | 结果前 5 行，人工抽检用 |

### 4.4 元信息

| 字段 | 说明 |
|---|---|
| `source` | `meeting`/`report`/`interview`/`ticket`/`synthetic` |
| `difficulty` | `easy`/`medium`/`hard` |
| `tags` | 自定义标签，如 `["时间变体","同比"]` |
| `annotator` / `reviewer` | 标注人 / 复核人 |
| `status` | `draft`/`reviewed`/`adjudicated`/`rejected` |
| `notes` | 易错点说明、争议记录 |

## 5. 时间表达清单（必须专门覆盖）

**时间解析建议用代码做，不要交给模型算。** 标注时明确写出解析结果，作为解析函数的测试用例。

| 口语表达 | 解析结果（granularity + range） | 备注 |
|---|---|---|
| 上个月 / 上月 | `month, last_month` | |
| 这个月 / 本月 | `month, current_month` | 通常数据未落定 → `provisional` |
| 今年以来 / 年初至今 | `month, year_to_date` | 高频且易错 |
| 前三季度 | `quarter, first_three_quarters` | 易错 |
| 去年同期 | `month, same_period_last_year` | 隐含同比 |
| 近半年 / 最近六个月 | `month, last_6_months` | 含当前月？需确认 |
| 2025 年 | `year, [2025-01-01, 2025-12-31]` | |
| 2025 年第三季度 | `quarter, [2025-07-01, 2025-09-30]` | |
| 上上周 | `week, last_two_weeks` | |
| 过去 12 个月 | `month, last_12_months` | 滚动窗口 |

**标注要求**：每一类时间表达**至少 3 条**，且"今年以来""前三季度""去年同期"必须各 ≥ 5 条。

## 6. `expected_sql` 的三条红线

| # | 红线 | 原因 |
|---|---|---|
| 1 | **必须真实执行过** | 未执行的 SQL 语法/字段名可能有错，会污染整个评估集 |
| 2 | **结果非空**（除非题目预期为空） | 空结果的用例无法判断正确性 |
| 3 | **必须由第二人复核** | 单人标注的错误率通常 10~20% |

### 6.1 SQL 编写约定

```sql
-- 必须包含：口径注释、时间字段、科室字段
-- 例：平均住院日（心内科，2026-08，按出院日期、出院科室）
SELECT
    SUM(occupy_bed_days) / NULLIF(COUNT(visit_id), 0) AS ip_los_avg
FROM dwd_fact_inpatient_discharge
WHERE discharge_date >= '2026-08-01'
  AND discharge_date <  '2026-09-01'
  AND discharge_dept_code = 'CARD'   -- dept_basis = discharge
  AND data_maturity IN ('settled','provisional');
```

- **禁止 `SELECT *`**
- **必须处理除零**：`NULLIF(..., 0)`
- **日期用半开区间** `[start, end)`，避免 `BETWEEN` 的边界问题
- ratio 必须 `SUM(num)/SUM(den)`，**禁止 `AVG(ratio)`**

## 7. 标注流程

```
① 采集问题池（约 500 条原始问题）
        │
        ▼
② 去重 + 规范化（保留原文、标注 source）
        │
        ▼
③ 按覆盖矩阵筛选 300 条（不足则补构造）
        │
        ▼
④ 双人独立标注（A、B 各自标全部 300 条）
        │
        ▼
⑤ 一致性计算（指标选择一致率 / Cohen's Kappa）
        │     一致率 < 85% → 重新对齐标注规范，重标
        ▼
⑥ 裁决（指标业务责任人裁定分歧项）
        │
        ▼
⑦ 脚本校验（validate_golden.py：必填/枚举/schema/SQL 可执行/分布）
        │
        ▼
⑧ 入库 v1，建立 CI 回归
        │
        ▼
⑨ 持续增补：线上打回案例 48h 内补入
```

### 7.1 工期与人力

| 环节 | 人力 | 工期 |
|---|---|---|
| 采集 | 产品 + 数据 1 人 | 3 天 |
| 双人标注 | 2 人（1 业务 + 1 数据） | 5 天 |
| 一致性检查 + 裁决 | 2 人 + 业务责任人 | 2 天 |
| 脚本校验 + 入库 | 1 人 | 2 天 |
| **合计** | **3 人** | **约 2 周** |

## 8. 一致性判定

```python
# 指标选择一致率
agreement = 两条标注 metrics 集合完全相同的条数 / 总数

# Cohen's Kappa（按 intent 分类）
kappa = (po - pe) / (1 - pe)
```

| 指标 | 门槛 |
|---|---|
| `metrics` 集合一致率 | ≥ 85% |
| `intent` 一致率 | ≥ 90% |
| Cohen's Kappa（intent） | ≥ 0.80 |
| `expected_sql` 结果一致率 | **= 100%**（不一致必须裁决） |

**分歧处理优先级**：业务责任人 > 指标字典定义 > 多数表决。

## 9. 常见标注错误（checklist）

| ❌ 错误 | ✅ 正确做法 |
|---|---|
| 把歧义问题直接标成确定答案 | 标 `requires_clarify=true` + `clarify_rule_id`，并在 `clarify_resolution` 写默认假设后继续标注后续字段 |
| `clarify_resolution` 自己编一个措辞 | **必须原样取自该规则的 `options`，或与该规则 `default` 完全一致**（标点除外）。语义层的 `apply` 段是按**字面**匹配的（docs/03 §6.1），自己编措辞会被判成"未声明映射"而拒绝出数。若确实需要一个新说法，先去 `ambiguity_rules.yaml` 的 `apply.values` / `alias_to_default` 里声明它。`python validate_golden.py --ambiguity ../semantic-layer/ambiguity_rules.yaml` 会在入库前拦住这类错误 |
| 时间只写"上月"不写解析结果 | 必须写 `time_spec` 的解析结果 |
| SQL 没跑过就填 | 必须执行并记录结果 |
| ratio 写成 `AVG(...)` | 必须 `SUM(num)/NULLIF(SUM(den),0)` |
| 科室名直接写"心内科" | 需确认是否对应 `dept_code = 'CARD'`，写清映射 |
| 越权题标成 `allow` | 越权题的 `permission_expect` 必须是 `deny` 或 `partial` |
| 全部来源于构造 | 构造占比 ≤ 15% |
| 忽略 `data_maturity` | 当月/当季数据须标注 `provisional` |
| 单位没统一 | 元 vs 万元必须在 `notes` 写清 |
| **同类问题有的标歧义、有的不标** | 反问策略必须自洽（见 §9.1）——同一歧义要么都问要么都不问，否则引擎无法拟合 |

## 9.1 样例集 v1.1 标注修正记录（口径一致性反推）

端到端管线（`engine/pipeline.py`）首次跑通后，Golden 集暴露出**标注自身的口径不自洽**。
按「Golden 集是最值钱的资产、也是唯一能在写代码前暴露口径分歧的东西」这一原则，
修正标注而不是迁就标注改代码。修正后样例集为 **31 条**。

| 用例 | 原标注 | v1.1 | 依据 |
|---|---|---|---|
| G0007 心内科上月平均住院日同比 | 不反问 | **反问 AMB-004** | 与 G0014「神经外科平均住院日」完全同构（点名科室 + 归属口径 supported=2），原来一个问一个不问，引擎无法自洽 |
| G0027 2025Q3 普外科出院人次 | 不反问 | **反问 AMB-004** | 同上，`ip_discharge_cnt` 归属口径 supported=3，歧义更严重 |
| G0028 全院医生手术量排名前20 | 不反问 | **反问 AMB-007** | 与 G0009「全院手术量」同构（都含裸「手术量」）。手术口径是等级评审关键指标，必须确认 |
| G0030 上个月住院收入怎么样 | 反问 AMB-002 | **不反问** | 问题已限定「住院收入」，范围歧义已消除；「是否含药品」按本院默认口径执行并回显、可切换（IN-01），不再打断用户 |
| G0031 上个月全院收入怎么样 | — | **新增，反问 AMB-002** | 替代被修正的 G0030，保证 AMB-002 仍有用例覆盖（裸「收入」未限定范围，会实质改变数值） |
| G0003 心内科收入（越权） | `dept_basis=order` | **改为 `belong`** | DSL 只有一个科室口径位；住院/门诊收入两指标的公共口径是 `belong`。原标注会先撞上「住院收入不支持 order」的校验错误，导致越权用例拿不到 `denied` |

**被推翻的两条旧词表设计**（见 [03 §6](../03-指标字典与语义层建模.md) / `ambiguity_rules.yaml`）：

- AMB-004 v1.0 用裸词表（科室收入/科室工作量…）→ 真正的归属歧义（G0014）反而漏反问。
  改为 `trigger_on: dept_mentioned`，按 registry 科室枚举判定「是否点名科室」。
- AMB-005（时间基准）改为 `ask_mode: echo_only`：本院对财务类已统一默认结算日，
  差异在口径卡片回显即可。若按裸词触发，反问率会接近 100%（AMB-006 同款教训）。

## 10. 持续维护机制

| 触发 | 动作 | 时限 |
|---|---|---|
| 线上用户点踩 | 该问题 + 正确答案补入 Golden 集 | 48 小时内 |
| 新指标上线 | 补 ≥ 8 条该指标用例 | 上线前 |
| 口径变更 | 受影响用例重跑 + 更新 `expected_sql` | 随变更 |
| 每季度 | 全量重跑，清理因历史数据回刷而失效的用例 | 季度 |
| 模型/提示词变更 | 全量回归，对比报告存档 | 每次 |

> ⚠️ **Golden 集必须纳入版本管理**（Git），每次变更有 commit message 说明原因。评估结论必须能复现（记录 Golden 集 commit hash）。

## 11.1 从 31 条扩到 300 条：先体检，再采集（**禁止脚本编造**）

脚本只负责体检与算缺口，**题目必须由人按 §2 的来源采集**：

```bash
python eval/check_coverage.py \
    --input eval/golden_set_sample.jsonl \
    --registry semantic-layer/metric_registry.yaml \
    --target 300 \
    --md eval/reports/golden_gap.md      # 退出码非 0 = 有缺口，可接 CI 卡入库
```

当前 31 条样例的体检结果（目标 300）：**42 项缺口**，主要是

- 规模缺 269 条
- 每指标 ≥8 条：多数指标只有 0~5 条（ratio 要求 ≥12，几乎全部不达标）
- 多指标组合 ≥20 条
- 问口径（meta）场景不足（现 3.2% < 5%）
- 时间表达：多数类型不足 3 条，"今年以来 / 前三季度 / 去年同期" 需各 ≥5 条

⚠️ **红线**：P2 构造占比 ≤15%。用脚本批量造 300 条会直接违反 §2.1，
导致分布偏斜、评估失真 —— 评估出来的高准确率是自欺欺人。
正确做法是按 `eval/reports/golden_gap.md` 的缺口清单，
带着清单去院周会纪要、月报季报、科室主任访谈、历史取数工单里逐条采集。
