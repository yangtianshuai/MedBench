# 12 · 身份认证与权限落地设计

> 与 [05 安全合规与权限](05-安全合规与权限.md) 的分工：05 回答「需要哪些合规能力」，本文回答
> 「从**当前这份代码**到可验收状态，具体改哪些点、按什么次序、怎么证明改对了」。
> 本文只覆盖三段：**身份（你是谁）→ 授权（你能看哪些范围）→ 审计（你做了什么）**。
> 数据侧的 RLS/脱敏已有实现，本文只做「接线」与「验证」，不重造。

---

## 0. 一句话问题定义

现有权限**判定逻辑是对的，信任链是断的**：RLS 落 SQL、门禁早于反问、越权预检不依赖模型——这些都对。
但「你是谁」由客户端在请求体里自己声明。合规评审的第一个问题就是它，而且当前实现里存在两个
**可被直接利用**的高危点（§1 的 S1 / S2）。

**这不是"再打磨一下"的缺口，是"能不能进入院方安全评审"的闸门。**

| 能力 | 位置 | 价值 |
|---|---|---|

### 1.2 缺口（按严重度排序）

**S1 · 零认证 + 高危默认值** ⛔
- 整个 `app/` 内没有任何鉴权依赖：全仓搜不到 `Depends` / token / Cookie 校验，
  `Authorization` 仅出现在 `app/routers/admin.py:228`（那是调用大模型时加的 Bearer，与用户身份无关）。
- 默认值是**身份冒用**：`AskRequest.user_id` 默认 `"u001"`（`app/models.py:11`，而 `u001` 是**张院长**）；
  同类默认值见 `app/routers/reports.py:22`、`app/routers/security.py:17`。
- 前端用下拉框自选身份（`app/web/index.html:53-62`）。
- 任何能访问服务端口的人，`POST /api/ask` 不传 `user_id` 即获得**院长视角、全院范围**。

**S2 · `guest` 被 `or ["*"]` 提升为全院无围栏** ✅ 已修复（v0.9）（本次盘查新发现）
```python
# app/routers/ask.py:28 与 app/routers/analysis.py:33
dept_scope=user["dept_scope"] or ["*"],
```
- `permission.resolve_user()` 对未知用户返回 `dept_scope: []`（`app/core/permission.py:46-48`）；
- `[] or ["*"]` → `["*"]` → 通配符；
- 连锁结果三处全部失效：越权预检因 `"*" in scope` 直接返回 None（`pipeline.py:610`）；
  科室越权检查因 `wildcard=True` 全部跳过（`pipeline.py:628,632`）；
  RLS 因 `"*" not in dept_scope` 为假而**完全不注入**（`sql_builder.py:306`）。
- 唯一还起作用的拦截是 `sensitivity == "restricted"` 的指标（`sql_builder.py:355-358`）。
  但 `ip_discharge_cnt` / `ip_los_avg` / `cmi` / `surgery_cnt` 等是 `sensitivity: internal`——
  **未授权访客可以正常问出全院出院人次、各科室平均住院日排名、CMI**。
- 也就是说，前端那个 `u999 未授权访客` 选项，当前不会拒绝，而是放行。

**实测验证**（用现有 `SQLBuilder` 直连跑，非推测；指标取 `ip_discharge_cnt` 出院人次，`sensitivity: internal`）：

| 用例 | `ctx` | 结果 |
|---|---|---|
| A | `{"role":"guest","dept_scope":["*"]}` | 生成成功，SQL 中 **无** `belong_dept_code`，`warnings=[]` → **全院数据可查** |
| B | `{"role":"科室主任","dept_scope":["0101"]}` | SQL 中**有** `belong_dept_code IN (...)` → 围栏正常 |
| C | `{"role":"guest","dept_scope":["*"]}` + `ip_revenue`（`restricted`） | 抛 `DSLError`（`sql_builder.py:357`）→ 唯一仍生效的门禁 |

结论：把 `guest` 挡在全院数据之外的，**只剩 `sensitivity == "restricted"` 这一层**；
`internal` 级别的指标（出院人次 / 平均住院日 / CMI / 手术量等）对未授权访客是敞开的。

**修复记录（v0.9，已落地）**：根因是「**空列表语义歧义**」——`[]` 被当成「未指定」，
而它的正确语义是「**无授权**」。修了 6 处，全部保持 fail-closed：

| # | 位置 | 改动 |
|---|---|---|
| ① | `app/routers/ask.py`、`app/routers/analysis.py`、`app/core/engine_bridge.py` | 去掉 `dept_scope or ["*"]` 兜底 |
| ② | `engine/pipeline.py`（`detect_out_of_scope_dept` / `check_permission`） | 空范围直接 `denied`（不再当成「无限制」） |
| ③ | `engine/sql_builder.py` | 显式空范围 `raise DSLError`（纵深防御，绕过管线也拦） |
| ④ | `app/core/permission.py`（`filter_metrics`） | 显式空 `visible_metrics` = 无授权，返回空集 |
| ⑤ | `app/models.py` + 各 router | `user_id` 默认值 `u001`（院长）→ `guest`（最小权限） |

**回归证据**：`python engine/pipeline.py --selftest` 新增 3 项（对照 / 空范围拒绝 / SQL 层兜底），
**16 项全过**（原 13 项无回退）；`python engine/sql_builder.py` 与 `attribution.py --selftest` 均通过；
真实 API 路径 `POST /api/ask`（`u999`）→ `status=denied`、`rows=None`、`sql=None`；
院长视角出数正常（2023 全年出院 59,653，与既有记录逐位一致）。

  > `ASK_AUTH_MODE=gateway/sso` 由网关注入身份才谈得上"可信"。

**S5 · 无用户生命周期与授权留痕**
- `app/config/roles.yaml` 是明文静态文件：无生效期、无变更审计、无离职失效机制（第 65-82 行的示例账号即正式形态）。
- 示例授权码与真实科室字典不一致：`roles.yaml:73` 写 `dept_scope: ["0101"]`，
  而 HIS 实测科室码是 6 位（如 `010303` 神经内科门诊）——**该账号实际查不到数据**，
  上线前未对齐会表现为「系统坏」而非「越权」，很容易被误判成 bug。

**S6 · 密钥明文落盘，与设计声明矛盾**
- `app/config.py:2` 声明「敏感信息只从环境变量读取，**不落盘、不入库**」；
- 但 `app/core/runtime_config.py:105-109` 的 `save()` 用 `yaml.safe_dump` 把
  `llm.api_key` 与 `datasource.his.password` **明文写入** `var/runtime_config.yaml`。
- 脱敏只做在 GET 路径（`masked()`，`runtime_config.py:163-178`），存储是明文。
  （当前该文件为 4 字节空配置，未泄露；但管理端一保存就会出现。）

**S7 · 多院区围栏「代码与配置已接线，数据源缺列」**
- ✅ `sql_builder` 已支持 `campus_scope` 注入围栏列，**列不存在时在生成 SQL 前**拒绝
  （`_rls_campus_col`），不会拼一条必然报错的 SQL；
- ✅ 调用方**已经传递**：`pipeline.ask(campus_scope=…)` 会做预检（`detect_out_of_scope_campus`）、
  门禁（`check_permission` 第 1.5 条）与 `ctx["campus_scope"]`；`roles.yaml` 有 `default_campus_scope`（三态），
  `auth_grant` 台账有 `campus_scope` 字段，`authz_sync.yaml` 有院区列名映射。
  （~~原记「调用方从不传递：`pipeline.py:828` 只构造 `{role, dept_scope}`」~~ —— 该结论已过时，见 §5.3 的 v0.20 更正。）
- ❌ **数据源没有院区列**：HIS 镜像 `PAT_VISIT` 未抽取该字段，ADS 宽表 `build_ads.py` 没建列，
  两份物理映射都显式写 `campus_code: null`。
- 结果：多院区授权**在数据层仍不可用**，但表现形式是"明确拒绝 + 说明原因"，
  而不是静默返回无权院区的数字（后者更糟：不报错，但答案是错的）。

**S8 · 无版本控制、无忽略规则**
- 项目无 `.git`、无 `.gitignore`；`var/` 下有 16 MB 的 `ads.db` 与审计库 `askdata.db`、多个日志。

**S9 · 执行层与目录层对 `internal` 的语义不一致** ✅ 已修复（v0.10）（修复 S2 时验证发现）
- **执行层**（`engine/sql_builder.py:359`）只对 `sensitivity == "restricted"` 做门禁
  → `internal` 视为「院内可看」；
- **目录层**（`app/core/permission.py` 的 `can_see_metric`）只对 `public` 放行，
  `internal` 与 `restricted` **都**要求角色的 `sensitive_metrics` 授权；
- 而 `app/config/roles.yaml` 只给部分角色配了该字段：`科室主任` / `运营管理部` / `医保办`
  **没有配** → 这些角色的指标目录与驾驶舱是 **0 个指标**。

- 影响：主任**能问出数**（`/api/ask` 不经过该过滤），但 `/api/reports/dashboard`
  与 `/api/semantic/metrics` 是空的 —— 典型「看得见却点不进去」。
- **已按 (a) 修复（v0.10）**，并顺带揪出**第三种 guest**：
  - 授权名单改为**只读语义层** `permission.restricted_metrics_roles`（唯一事实来源）——
    执行层与目录层从此必然一致；`roles.yaml` 的 `sensitive_metrics` 降级为回退；
  - `resolve_user` 的「未知用户」分支与 `roles.yaml` 的 `guest` **合并为同一条组装路径**：
    前者原本漏了 `visible_metrics`，导致未知用户反而看得到指标目录
    （即「两个 guest 语义不同」）；
  - [docs/03 §2.0](03-指标字典与语义层建模.md) 补上三级语义与可见性规则表（根治）。
- **回归**：新增 `python -m app.core.permission --selftest`，含
  「全角色 × 全指标」一致性对拍断言，**5 项全过**；
  实测 `/api/reports/dashboard` 与 `/api/semantic/metrics`：
  `科室主任` 由 **0 → 20**（与执行层一致），`u999` 为 **0**。
- **行为变化须知**：`科室主任` / `运营管理部` / `医保办` 的指标目录由 **0 → 20**。
  若院方认为某角色不应看 `restricted` 指标，**改语义层 `restricted_metrics_roles` 一处即可**，
  执行层与目录层同时生效 —— 这正是单一事实来源的价值。

## 3. 身份：从「前端自报」到「后端授信」

### 3.1 目标链路

```
浏览器 → 院内 SSO / 统一网关 → 本服务会话 → 服务端解析主体
       → 派生 (role, dept_scope, campus_scope) → 注入 pipeline
       → 请求体中的 user_id 一律忽略（并记一条告警审计）
```

### 3.2 对接形态三选一

| 形态 | 适用 | 优点 | 关键风险 |
|---|---|---|---|
| **反向代理注入可信头**（推荐首选） | 院内已有 IIS/Nginx 集成认证 | 不改应用协议、最快落地 | 必须**剥离客户端伪造的同名头**，只信任网关来源 IP |
| CAS | 院方已有统一身份平台（最常见） | 标准、院方熟悉 | 票据校验与服务端会话要自己做对 |
| OIDC | 院方为新一代平台 | 生态好 | 医院内网较少见 |

**无论选哪种，落地顺序都一样**：先确认院方能提供什么（见 §3.5），再选形态——不要先写代码。

### 3.3 会话与票据

- 服务端会话，Cookie 置 `HttpOnly` + `SameSite=Lax`（内网 HTTPS 时加 `Secure`）；
- 会话内缓存主体（角色/范围），每请求只做内存查表，**不回源 SSO**（否则问数首屏会被 SSO 拖慢）；
- TTL：绝对 8 小时 + 空闲 30 分钟；管理端单独更短（15 分钟）；
- 支持单点登出；登出后立即失效服务端会话（不能只清 Cookie）。

### 3.4 迁移策略（必须能灰度，不能一步到位）

新增 `ASK_AUTH_MODE = demo | gateway | sso`：

| 取值 | 行为 | 安全闸门 |
|---|---|---|
| `demo` | 保留示例身份（当前形态） | **启动时强制校验**：仅允许绑定 `127.0.0.1` 且 `ASK_ENV=demo`，否则拒绝启动并报错。防止 `demo` 被带上线 |
| `gateway` | 信任网关注入头 | 仅接受配置白名单内的来源 IP，服务端剥离同名头 |
| `sso` | CAS / OIDC 自校验票据 | 票据校验失败一律 401，不降级为匿名 |

管理端在 `gateway/sso` 模式下需**额外一层角色校验**（`信息科` 且来自管理网段）。

> **实现说明（v0.18）**：上表三态中的"安全闸门"一列不是意图，是代码里可验证的行为 ——
>
> | 表格里的要求 | 实现位置 | 怎么自己验 |
> |---|---|---|
> | `demo` 非环回即拒绝启动 | `app/core/security_gate.py`（启动闸门 + 请求级兜底两道） | `python -m app.core.security_gate --selftest` |
> | `gateway` 只信白名单来源 + 剥离同名头 | `ASK_TRUSTED_PROXIES`（支持 CIDR）；入口中间件 `main._identity_guard` **删除**非可信来源的身份头 | `python -m app.core.identity --selftest` |
> | `sso` 票据校验失败一律 401，不降级匿名 | `app/core/identity.py`（CAS：JSON/XML 双路解析；OIDC：`state` 防重放）；无会话即 `login_required` | `python scripts/check_auth_flow.py` |
>
> 另外两条实现上的取舍，值得在评审时说明：
> - **会话只证明工号**，授权每次按工号重新解析 —— 转岗/离职在院内系统改一次即生效，
>   不必等 8 小时会话过期（这也是 §4.2"不建第二套主数据"的前提）。
> - **登出必须是服务端失效**：只清 Cookie 只是"请用户忘掉旧值"，旧 Cookie 照样能用。
>   验收用例 H6 就是拿登出后的 Cookie 再访问，必须 401。

### 3.5 需院方提供的对接清单（先要东西，再动手）

1. 统一身份平台类型与地址（CAS protocol / OIDC issuer）→ `ASK_CAS_BASE` / `ASK_OIDC_ISSUER`；
2. 属性字段映射：工号、姓名、科室、岗位、院区——**哪些字段可信** →
   `ASK_ATTR_USER` / `ASK_ATTR_NAME` / `ASK_ATTR_DEPT` / `ASK_ATTR_CAMPUS`；
3. 测试账号 ≥ 3 个（院级 / 科室级 / 无权限）；
4. 证书与网络策略（本服务到 SSO 的出向访问）→ 内网自签证书请装 CA，不要关卡校验
   （`ASK_SSO_VERIFY_TLS=0` 只在临时排查时用）；
5. 管理网的来源网段（用于管理端二次校验）→ `ASK_TRUSTED_PROXIES`。

**这五项之外的东西都已经就绪** —— 联调时改的是环境变量，不是代码。
缺哪一项不会"静默降级"：启动日志会逐条打印，登录页也会直说缺什么。

### 3.6 本地账号兜底（`ASK_AUTH_LOCAL`）✅ **已落地（v0.21）** —— 与 SSO **长期并存**

前提：院方统一身份平台短期内接不上，但系统必须能让人登录用起来；且院方要求
**本地账号长期保留作为兜底**，不做"过渡期用完即删"。

结论：**不自建第二套权限**，只补一个"本地凭证"入口。权限仍 100% 来自 §4 的授权台账。

#### 3.6.1 两条轴必须分开，否则会做出第二套权限

| 轴 | 谁负责 | 本地账号是否改变它 |
|---|---|---|
| 「你是谁」（认证） | 本地口令 / SSO 票据 / 网关头 | 新增一种**凭证来源** |
| 「你能看什么」（授权） | `auth_grant` 台账（§4.2） | **完全不改** |

这样 SSO 联调完成后，换的只是"凭证怎么来"：台账、审计、RLS、导出水印、会话机制一行都不用动。

#### 3.6.2 开关与三个档位

`ASK_AUTH_LOCAL = off | breakglass | primary`（默认 `off`）

| 档位 | 语义 | 适用 |
|---|---|---|
| `off` | 无本地登录入口（现状） | 院方 SSO 已稳定 |
| `breakglass` | SSO 是主入口，本地登录是**应急通道**：账号数受控（建议 ≤5）、必须配 `expires_at` 与 `reason`、默认 `disabled`，需要时由管理员显式启用 | **长期兜底的推荐档位** |
| `primary` | 本地账号为主入口（SSO 还没接上时）；SSO 若已配置仍可作第二入口 | 联调空窗期 |

`ASK_AUTH_MODE`（demo/gateway/sso）语义**不变**。本地登录不需要改它 —— 因为
`identity._resolve_sso()` 本来做的就是"从服务端会话解析主体"，与凭证由谁签发无关。

#### 3.6.3 表结构

```sql
CREATE TABLE IF NOT EXISTS local_user (
  user_id        TEXT PRIMARY KEY,        -- 工号，与 auth_grant.user_id 同一个键
  name           TEXT NOT NULL,
  pwd_hash       TEXT NOT NULL,           -- scrypt$n$r$p$salt$hash（参数随哈希存，便于日后升级）
  pwd_updated_at REAL,
  must_change    INTEGER DEFAULT 1,       -- 建号/重置后强制改密
  status         TEXT DEFAULT 'disabled', -- active / disabled / locked
  failed_count   INTEGER DEFAULT 0,
  locked_until   REAL,
  last_login_at  REAL,
  expires_at     REAL,                    -- 账号有效期：兜底账号也必须有失效日
  created_by     TEXT,
  created_at     REAL,
  reason         TEXT                     -- 建号依据（与台账"依据必填"同一条纪律）
);
```

不存明文、不用可逆加密。口令参数走配置（`ASK_LOCAL_PWD_MIN_LEN` / `ASK_LOCAL_MAX_FAILS`
/ `ASK_LOCAL_LOCK_MINUTES`），不在代码里写死。

其中长度下限默认 **8 位**（v0.23 起，此前 12 位），且 `local_accounts.SECURITY_FLOOR_LEN = 8`
是代码里的**硬下限**：`ASK_LOCAL_PWD_MIN_LEN` 只能往上调 —— 现场一次误配（写成 4）
不该让全线口令一起变弱。前端提示读的也是同一个 `pwd_min_len()`，避免"界面说至少 4 位、
后端拒 8 位以下"这种自相矛盾。所有口令输入框都带「小眼睛」（只切 `input.type`，值不复制）。

#### 3.6.4 接口（全部挂 `/api/security`，沿用现有命名）

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /auth/local/status` | 公开 | `{enabled, mode}`：前端据此决定是否渲染本地登录表单（不靠猜） |
| `POST /auth/local/login` | 公开（限速 + 锁定） | 校验口令 → 复用 `session_store.create(auth_mode="local", auth_source="local")` → 发**同一种不透明令牌 Cookie** |
| `POST /auth/local/password/change` | 本人 | 只改**自己的**口令；`must_change=1` 时其它接口一律 409（登出/改密除外） |
| `GET /local/users` | 管理员 | 清单（**不含哈希**） |
| `POST /local/users` | 管理员 | 建号：工号 / 姓名 / 依据 / 有效期 |
| `POST /local/users/status` | 管理员 | 启用 / 停用 / 解锁 |
| `POST /local/users/password` | 管理员 | 重置：一次性初始口令 + `must_change=1` + **撤销该人全部会话** + 审计 |

> ★ **"只由管理员重置" ≠ "管理员知道用户的口令"**。管理员拿到的是**一次性初始口令**，
> 用户首次登录必须改密，之后管理员也无从得知 —— 否则口令就是共享凭证，
> 审计里"这条数是谁问的"直接失效（等保问的第一句就是这个）。
>
> 自助找回（忘记密码）不做：院里没有可用的短信/邮箱通道，做了也只能靠人工核身，
> 不如把"人工核身 + 管理员重置"这条唯一路径写清楚。

#### 3.6.5 复用既有机制（不新开一套）

| 既有能力 | 复用方式 |
|---|---|
| 会话（§3.3） | 完全复用：同一张 `user_session`、同一个 Cookie、同一套绝对/空闲超时与 `revoke_user` |
| 审计（§6.2） | 登录成功 / 失败 / 锁定 / 重置 / 停用 → `auth_event`；`auth_source="local"` 与 `cas`/`oidc` 可区分 |
| 台账（§4.2） | 权限按工号解析；**停用本地账号不自动删授权**（保留"他曾经有什么"），但管理端提示"该工号已停用仍有授权" |
| 启动自检（§7 A4） | 新增 4 条：档位非 `off` 时至少一个 `active` 账号；存在 `must_change` 未改的账号 → 告警；`breakglass` 档位账号数超上限 → 告警；`primary` 档位下演示切换器必须关闭 |
| 界面 | 登录页在非 `off` 档位渲染工号+口令表单；管理端新增「本地账号」页（导航"治理"组） |

#### 3.6.6 长期并存的风险与补偿（这条要让院方知道）

| 风险 | 补偿 |
|---|---|
| 口令比 SSO 弱（弱口令 / 共享 / 撞库） | scrypt 哈希 + 失败锁定（建议 5 次锁 15 分钟）+ 长度复杂度 + 首登改密 + **独立限速** |
| 影子账号长期存在，人走了没人销号 | 账号必须有 `expires_at`，到期自动失效；管理端"30 天内到期"提示（复用台账的到期提醒） |
| "这次登录走的哪条路"说不清 | 每条会话记 `auth_source`；管理端常驻"近 30 天本地登录 N 次" |
| 管理员成为单点（掌握重置能力） | 重置动作进 `auth_event` 且不可改；建议双人复核（A 建号、B 启用） |
| 本地账号被当成"绕过 SSO 的后门" | `breakglass` 档位下默认 `disabled`，启用必须填依据与失效日；账号命名带前缀（如 `emg001`）便于审计检索 |

## 4. 授权：从静态 YAML 到可治理授权

### 4.1 主体模型（最小集）

```
user_id(工号) × role(岗位) × dept_scope(科室集合) × campus_scope(院区集合) × 生效期 × 来源
```

### 4.2 授权来源：不建第二套主数据

- **以院内 HRP/HIS 组织架构为准**，本产品只维护「映射表 + 增量同步」，不自己做人事主数据；
- `roles.yaml` 从「数据源」降级为「**角色定义模板**」（角色能做什么：可见指标、能否导出、能否看 SQL），
  「谁能担任该角色、覆盖哪些科室」移到数据库表中，由同步任务维护；
- 好处：离职/转岗在院内系统处理一次即全系统生效，不需要在问数系统里再点一遍。

> **实现说明（v0.19）**：本节已落地。`auth_grant` 台账 + `app/core/authz_store.py`（判定）、
> `app/core/authz_sync.py`（映射与计划）、`scripts/sync_authz.py`（CLI 入口）、
> `semantic-layer/authz_sync.yaml`（岗位→角色、科室名→科室码的映射表）。
>
> 落地过程中**新加的三条约束**（原文没写，但缺了它就等于没做）：
>
> | 约束 | 缺了会怎样 |
> |---|---|
> | **依据必填**（`source_ref`：组织架构版本 / 工单号 / 备案号） | 半年后没人答得出"这个权限是谁给的"——这正是 §4.4 要回答的问题 |
> | 同一人同一时刻**只有一条**有效授权（改授权 = 撤旧 + 写新） | 两条并存时"谁生效"取决于查询顺序，等于权限随机 |
> | 台账里的空范围按**无授权**处理，**不回落**角色 `default_dept_scope` | 同步任务漏填会被兜底成"全院"——把"漏填"变成"越权" |
>
> 以及两个必须显式打开的**危险操作**（默认关闭，写在 `--help` 里）：
> `--revoke-missing`（一份只覆盖部分科室的导出会撤掉全院权限）、
> `--apply`（默认 dry-run；批量改授权不该是"点一下试试"）。
>
> **验收观察点**：`python scripts/check_auth_flow.py` 的 H13~H20。
> 其中 H13 是一条容易踩的"鸡生蛋"：`ASK_AUTHZ_FROM=table` 且台账为空时**没有人是管理员**，
> 管理端进不去 —— 首启必须先用命令行跑一次迁移。
>
> **待院方配合**：组织架构的导出接口/文件格式与岗位命名（列名映射在 `authz_sync.yaml` 的
> `fields` / `role_map` / `dept_map` 三段，联调时只改配置）。

### 4.3 科室变更（SCD2）

- 对账锚点必须是 `dept_code`，**不是科室名称**（更名会让按名称的授权静默失效或越权）；
- 科室合并时，旧授权需按预设规则迁移（合并到目标科室或收紧为无权限），迁移动作要留痕；
- 可验证断言：**任一时刻，某用户的有效科室集合 = 该时刻组织架构映射的结果**（可用于回归）。

> **实现说明（v0.19）**：台账只存科室码；科室名进不来 —— 导入时必须经 `dept_map` 翻译，
> 翻不出来就**整体不导**并逐条列出（宁可人工补完映射，也不猜：猜错就是给错人开错范围）。
> 科室合并/更名走 `dept_alias`（旧码→新码）并在导入时留痕。
> **为什么不按名称匹配**：更名后旧授权会匹配不上而**静默消失**，当事人第二天发现查不了数，
> 而系统里没有任何记录说发生过什么。这一条对应 `authz_sync.map_rows()`。

### 4.4 授权变更留痕

- 表结构：`who / when / grantee / scope / action / 依据(备案号或工单号)`，**只允许追加**；
- 与 §6 的审计库分开存储（授权变更 ≠ 数据访问），但同样不可篡改。

> **实现说明（v0.19）**：`auth_grant_log` 表，只允许追加（没有 UPDATE/DELETE 接口），带哈希链
> （与 `audit_log` 同一做法与同一局限，见 §6.2）。**`actor` 与 `grantee` 是两个字段**：
> 同步任务改的和"某人手动提权"必须能区分 —— 合成一个字段，审计时就说不出是谁下的手。
> 撤销**不删行**：删掉之后"他曾经有过什么权限"就查不到了，而这恰恰是审计时唯一需要的答案。
> 台账与留痕都对管理员开放查看（`/api/security/grants`、`/grants/log`），且台账本身**只有管理员能读** ——
> 它是"谁在哪个科室、什么岗位"的名册，比指标目录更敏感。

## 5. 数据侧强制执行

### 5.1 五段式围栏（次序不可换）

```
① 身份授信（§3）→ ② 越权预检（已有）→ ③ SQL 层 RLS（已有）+ 院区（待接线）
→ ④ 结果裁剪兜底 → ⑤ 小样本抑制/上卷
```

③ 是主防线，④ 是兜底：即使 ③ 因配置错误漏了，④ 也不能让越界分组出现在响应里。

> ⚠️ **v0.19 修正：③ 曾经是"看起来有、实际不通"的**。RLS 注入的列名被**写死**为
> `belong_dept_code`，而这一列在两条路线上的真实名字都不是它
> （HIS：`DEPT_DISCHARGE_FROM`；ADS 宽表：`discharge_dept_code`）。
> 后果：**任何科室级授权的用户一条数都问不出来**，而全院范围的用户完全无感
> （RLS 对 `["*"]` 不注入）—— 最容易被误判成"这个指标没数据"的一类故障。
> 为什么一直没发现：单元测试只断言"SQL 字符串里出现了 `belong_dept_code`"，
> 从未把这条 SQL 真正执行过。
>
> 现在改为从语义层 `permission.rls` 取**逻辑名**、经物理映射解析成**真实列**
> （`sql_builder._rls_dept_col` / `_rls_campus_col`）；数据源没物化某列时
> **在生成 SQL 之前**报可诊断错误，而不是把 `no such column` 丢给运维去猜。
> 回归：`engine/sql_builder.py` 的"RLS 列解析"四条 + `scripts/check_auth_flow.py` 的 H14。

### 5.2 修 `guest` 漏洞（最小改动）

不要在各 router 里做 `or ["*"]` 兜底，改为**在语义层显式区分两种空**：

- `["*"]` = 明确的全院授权；
- `[]` = **无任何范围**（必须拒绝，不得兜底成通配符）。

调用方禁止自行补默认值；`resolve_user()` 直接返回可用于判定的范围，`None`/空一律按「无范围」处理。
对应回归用例见 §7 的 A2。

### 5.3 多院区围栏接线

| 角色模板 | `roles.yaml` 的 `default_campus_scope`（院长等 ``["*"]``；科室主任**刻意不配**） | ✅ |

### 5.4 患者级门禁的产品化（加流程，不是加白名单）

`forbidden_fields`（`metric_registry.yaml:824`）保持不变——患者级字段在问数场景**永远不可 SELECT**。
「需要审批才开」指的是另一条独立链路，而不是放宽本链路：

```
申请（事由 + 期限 + 患者范围）→ 双人复核 → 临时授权（自动到期）
→ 每次调用全量审计 → 到期自动回收 → 定期复核清单
```

技术要点：临时授权只针对**受限视图**，不影响问数语义层的字段白名单。

## 6. 审计与留痕（等保口径）

### 6.1 已记录的字段（保留）

`who / when / question / status / intent / metric_code / dsl / sql / row_count / result_hash / latency`
（`app/core/engine_bridge.py:132-137`）——字段设计已经够用。

### 6.2 不可篡改：本地 SQLite 不满足

- 审计写**独立存储**（院内既有数据库或 WORM/对象存储），不与业务元数据同库；
- 每条记录携带前一条的哈希（**哈希链**），提供 `verify_chain()` 自检；
- 审计表权限：只允许 INSERT，禁止 UPDATE/DELETE；
- 理由：审计库当前落在 `var/askdata.db`，DBA 可直接改，等保测评不会通过。

> **实现说明（v0.20）**：已落地 `app/core/audit.py`（独立库 `var/audit.db`）。
>
> ⚠️ 先说一句必须写进方案的话：**"挪到另一个库"本身并不解决问题** ——
> 能改一个库文件的 DBA，两个库都能改。真正起作用的是下面三条，
> 缺任何一条，"日志没被改过"这句话都撑不住：
>
> | 防线 | 做法 | 防住 | **防不住** |
> |---|---|---|---|
> | ① HMAC 链 | 链哈希用 HMAC-SHA256，**密钥在库外**（`ASK_AUDIT_HMAC_KEY` 或独立密钥文件） | 能改库但**没有密钥**的人：算不出正确的链（重算整链也不行） | 同时拿到密钥与库权限的人 |
> | ② 链锚 | 每 N 条把 `(条数, 尾哈希, 密钥指纹)` 追加到**另一个位置** | 整链重算、**截断尾部** | 锚文件被一起改的人（故建议锚指到另一块盘/另一台机器） |
> | ③ 库级只允许追加 | SQLite 触发器对 `UPDATE`/`DELETE` 直接 `RAISE(ABORT)` | "顺手改一行"这类绝大多数情况 | `DROP TRIGGER` 后再改（由 ① 兜住） |
>
> **②不是可选项**：只做哈希链**发现不了"删掉尾部若干条"** ——
> 删掉最后 N 条之后，剩下的链依然逐条自洽。这是哈希链最容易被高估的地方，
> 也是本轮自测里专门用一条用例锁住的行为（`test: 只删尾部 → 被链锚抓到`）。
>
> **一条必须写进交接文档的运维风险**：审计密钥丢了，历史链就**永久无法校验**。
> 它很容易发生 —— 密钥文件默认自动生成在 `var/` 下，清理目录、换机器、容器重建都会带走它。
> 所以：① 密钥与库一起纳入备份；② 或用 `ASK_AUDIT_HMAC_KEY` 由信息科统一分发；
> ③ **CLI 与服务必须用同一把密钥**（`sync_authz.py` 写留痕时也用这把），
> 否则 CLI 写的行会看起来像"被改过"（哈希对不上）。锚记录里的 `key_id` 就是用来
> 区分"记录被改"与"换了密钥"的 —— 两者都表现为校验失败，但处理方式完全不同。
>
> **遗留数据**：改造前写在 `var/askdata.db` 的行由 `audit.migrate_from_meta()` 一次性搬走
> （启动时自动执行、幂等）。搬迁的行一律标为 **legacy、不回填哈希** ——
> 给它们补一条链等于**声称一段从未存在的保护**；它们仍可被**旧算法单独校验**
> （`legacy_chain`），如果连旧链都对不上，说明这些行在迁移前就被改过，这时要明说。
>
> **顺带修掉的一个真 bug**：迁移时长尾字段（`row_count` / `latency_ms`）被"顺手"把 NULL 补成 0，
> 导致旧链全部对不上 —— 升级当天就会看到"遗留记录被改过"这种吓人但完全错误的结论。
> 迁移必须**逐字保真**。
>
> **验收**：`python -m app.core.audit --selftest`（13 项，含"删一条 + 用公开算法重算整链仍被判失败"
> 与"12 并发写入不撞号"）、`python scripts/check_auth_flow.py` 的 H21 系列。
> 并发那条来自一次真实故障：读链尾与插入没串起来 → 撞 `seq` → **整个 `/api/ask` 500**。
> 审计写不进去不该把业务打挂，这个耦合必须断掉。

### 6.3 审计自身要授权

- `/api/security/audit` 限管理员角色；普通用户只能查自己的记录；
- `/api/trust/snapshots` 限「本人」或管理员（快照含真实数值）。

### 6.4 导出防伪

- 导出内容**必须由服务端按 `answer_id` 从快照取**，不接受客户端提交 `rows`
  （当前 `reports.py:58` 接受，属可伪造）；
- 水印增加**导出流水号 + 校验位**，与导出日志一一对应，便于反查。

> **实现说明（v0.20）**：两条都已落地。
> - "只接受 `answer_id`"自 v0.16 起生效（`docs/13 §7 C5`）；本轮补的是**流水号**：
>   格式 `EX-YYYYMMDD-SSSS-CC`，`CC` 是 ISO 7064 MOD 97-10 校验位
>   （`app/core/export_trace.py`）。
> - 反查接口 `/api/reports/exports/verify?serial=…`（管理员）返回**三态**，
>   必须区分清楚，否则会把"抄错号"当成"伪造文件"：
>   `format_ok=false`（编号不合法 = 抄错/改过一位）→ 不是本院文件；
>   `format_ok=true, found=false`（格式对但日志没有 = **伪造**）；
>   `found=true`（确实导出过，给出操作人/快照/时间）。
> - **诚实边界**：校验位不是加密，**不阻止伪造** —— 谁都能自己算一个合法编号。
>   它阻止的是"编号看着像真的"：伪造者还得让这个编号在 `export_log` 里真实存在，
>   而那需要写审计库的权限。所以它的定位是"配合水印反查"，不是"防伪水印"。
> - 顺序上**先记流水号、再写水印**：反过来会出现"文件里有号、日志里查不到"的窗口，
>   而那正是反查时最尴尬的情况（分不清是伪造还是刚导完还没来得及记）。

### 6.5 异常访问检测

- 规则示例：同一用户 10 分钟内跨科室查询 > N 次、连续枚举科室、单日导出 > N 次；
- 动作：告警（通知信息科）+ 限流，**不自动封禁**（避免误伤管理岗的正常巡检）。
