# 08 · MVP 实施排期与团队

## 1. 总体路线图

```
P0 数据盘点与口径梳理（4~6 周）★ 最重
   ↓
P1 MVP：单场景 30 指标（8~10 周）
   ↓
P2 语义层完善 + 自由问数（8~12 周）
   ↓
P3 智能洞察：归因 / 异常 / 预测（12~16 周）
   ↓
P4 行动闭环：预警 → 工单 → 反馈 → 回流（持续）
```

> **P0 占 50~60% 工作量**，且不可压缩。口径没谈拢就上 LLM，只会得到"看起来聪明但数字不对"的产品，且永久失去用户信任。

## 2. P0：数据盘点与口径梳理（4~6 周）

### 2.1 任务清单

| # | 任务 | 产出 | 责任方 | 工期 |
|---|---|---|---|---|
| P0-1 | 数据源盘点 | 《数据源清单》（系统、库类型、表、字段、更新频率、负责人） | 信息科 + 数据团队 | 1 周 |
| P0-2 | 接口与权限申请 | 只读账号、抽取窗口、网络策略 | 信息科 | 1 周（并行） |
| P0-3 | 主数据现状调研 | 《字典映射现状报告》（覆盖率、冲突点） | 数据团队 | 1 周 |
| P0-4 | **业务口径访谈** | 《指标字典 v0》（30 个核心指标定义） | 数据 PM + 业务 | 2~3 周 |
| P0-5 | 口径确认会 | 指标定义单签字（医务/财务/医保/院办） | 业务责任人 | 1 周 |
| P0-6 | 数据质量初评 | 空值/异常/映射缺失报告（可跑 Achilles） | 数据团队 | 1 周（并行） |
| P0-7 | 场景与角色确认 | MVP 场景定义 + 权限矩阵 | 产品 + 院办 | 1 周 |

### 2.2 P0 的关键会议

**口径确认会**是 P0 最重要的一场会。建议：

- 参会：医务处、财务处、医保办、运营管理部、信息科、院办（决策人）
- 议题：逐条过 30 个指标的定义、公式、时间口径、科室口径、责任人
- 产出：**每个指标有且仅有一个"说了算"的人**
- 常见争议：药占比是否含中草药、收入是否含其他收入、科室归属口径 → **当场拍板并书面记录**

> 💡 经验：这场会如果只叫了信息科，等于没开。业务口径必须业务拍板。

## 4. 团队配置

### 4.1 MVP 阶段（P0 + P1，约 16 周）

| 角色 | 人数 | 职责 | 关键能力 |
|---|---|---|---|
| **产品经理**（兼业务 BA） | 1 | 口径梳理、场景定义、验收 | 医院业务理解 + 数据产品经验 |
| **数据工程师** | 2 | 抽取、建模、跑批、质量 | SQL + dbt + Doris/Spark |
| **后端工程师** | 2 | 语义层服务、查询生成、权限、API | Java/Python + 数仓接口 |
| **算法工程师** | 1~2 | 问数引擎、提示词、召回、评估 | LLM 应用 + RAG + 评估体系 |
| **前端工程师** | 1 | 对话界面、图表、驾驶舱 | React + ECharts/Superset 集成 |
| **运维/DBA** | 0.5 | 部署、监控、GPU 运维 | K8s/Docker + Linux |
| **业务专家（兼职）** | 1 | 口径拍板、验收 | 医务/运营/财务背景 |

**总计：8~9 人（含兼职）**

### 4.2 P2~P4 扩编建议

| 阶段 | 新增角色 | 说明 |
|---|---|---|
| P2 | +1 数据工程师（OMOP/科研方向） | 建 CDM |
| P3 | +1 算法（时序/归因） + 1 数据 PM | 预测、异常检测 |
| P4 | +1 后端（工单/闭环） + 1 运营 | 行动闭环需要运营推动 |

## 8. 推广策略（决定生死的一环）

| 阶段 | 动作 |
|---|---|
| 上线前 2 周 | 找 3~5 位"种子用户"（最好是爱用数据、有影响力的主任）深度试用并收集反馈 |
| 上线周 | 院周会演示；准备 10 个"常见问题"卡片贴在科室 |
| 上线后 1 月 | 每周发布《问数排行》（哪些指标被问最多）+ 新指标上线通知 |
| 持续 | 每月与业务复盘：哪些问题答错了 → 补进 Golden 集 → 下个版本修复 |
| 激励 | 对提出有效反馈/贡献指标定义的科室给予正向反馈（院内网通报） |

> **最容易被忽略的一点**：问数产品是"信任生意"。前 3 个月的口碑决定了它是被当工具用还是被当玩具弃。宁可慢一点、指标少一点，也要保证每一个答案都对。

## 9. 产品化收敛清单（原型 → 可交付）

> 判断依据：代码现状盘点（[docs/12 §1](12-身份认证与权限落地设计.md)）与产品功能设计（[docs/11](11-产品功能设计.md)）。
> §3 回答「**做什么功能**」，本节回答「从当前原型形态到**可装机、可日用、可交付**，
> 还差哪些**非功能**的东西」——这类缺口最容易被排期忽略，却最直接决定「像玩具还是像产品」。

### 9.1 四类缺口与水位（2026-10 盘点）

| # | 缺口 | 现状 | 收敛目标 | 判定标准（可验收） |
|---|---|---|---|---|
| G1 | **交付形态** | 只有 `README.md` + `requirements.txt`；启动靠手敲 `uvicorn`；无容器、无 CI、无版本控制、无 `.gitignore` | 容器化一键部署 + 配置分层 + 升级回滚 + 健康检查 | 拿一台院内测试机、一个真实账号，**非开发人员能从零装起来** |
| G2 | **身份与权限** | 零认证；`user_id` 由前端传入（默认值已修为 `guest`）；行级围栏已落 SQL 层 | SSO + 后端授信 + 多院区围栏接线 + 授权可治理 | [docs/12 §7](12-身份认证与权限落地设计.md) 的 A/B/C 三组用例全过；检索不到「请求体 `user_id` 决定授权」 |
| G3 | **语义层治理** | 指标定义与物理映射已配置化、可热更新；但后台仅 API 骨架（`semantic.py` 67 行），责任人/审批/争议下线未成流程 | 指标注册 → 审批 → 变更留痕 → 争议下线 → 对账 的完整**人用**流程 | 管理员**独立完成**一次「注册 → 上线 → 对账」闭环，全程不碰命令行 |
| G4 | **数据地基** | 仅住院域 5 个指标真出数；门诊主表近空、`DRG_DETAIL` 止于 2019-06；ADS 为本地 SQLite。多源**注册与按源探测已可配**（v0.11），但 LIS / EMR / 医保 / HRP 尚未实际接入 | 门诊域接入 + 多源逐个接入（抽取层）+ DRG/医保域摸底 + Doris 实环境验证 | 门诊域可出数且与 HIS 报表对账；Doris 上复现性能结论；新源接入**只改配置不改代码**（`sources.yaml` + `source_domains.yaml`） |

### 9.2 合规前置项时间表（**不完成不得进入 M6 灰度**）

挂到 §3 的周次；标 ★ 为硬门禁，未过则 M6 顺延。

| 周次 | 事项 | 依赖 | 验收 |
|---|---|---|---|
| W1 ★ | 修空范围通配符 + 默认身份（S2） | 无 | ✅ 已完成（v0.9，端到端 16 项自测） |
| W1 | 三级权限语义对齐 + 唯一授权来源（S9） | 无 | ✅ 已完成（v0.10，5 项一致性对拍） |
| W1 ★ | 建仓库 + `.gitignore`（排除 `var/`：内含审计库与 16 MB ADS） | 无 | `git status` 不含 `var/` |
| W1~W3 ★ | 身份授信开关 + 会话（`demo` / `gateway` / `sso`） | 院方 SSO 信息（[docs/12 §3.5](12-身份认证与权限落地设计.md)） | A1~A4 用例通过；`demo` 模式绑定非本机则**拒绝启动** |
| W2 ★ | 管理端鉴权 + 数据源改动二次确认 | 身份授信 | 未授权角色改数据源 → `403` |
| W2 ★ | 密钥不留盘（改环境变量 / 密钥管理） | 无 | `var/` 内无明文密钥 |
| W3 ★ | 审计 / 快照 / 导出接口鉴权与防伪 | 身份授信 | D1~D3、E1~E4 用例通过 |
| W2~W5 | 授权表 + 组织架构同步（不建第二套主数据） | HRP/HIS 只读接口 | B5：离职账号自动失效，无需人工 |
| W5 | 科室 SCD2 迁移 + `campus_scope` 接线 | 院区字典 | B3、B4 用例通过 |
| W5~W6 | 审计独立存储 + 哈希链 | 院内 DB | D2：改一行即校验失败 |
| W9 | 异常访问检测（跨科室枚举 / 导出频次） | 审计独立存储 | 触发告警但**不自动封禁** |

> 💡 **执行建议**：W1 的三项（S2 / S9 / 建仓库）**不依赖任何院方输入**，属「半天级工作量、
> 但后果最重」的类型，应当立刻完成 —— 而不是等排期走到 W1。
> 其中 S2 与 S9 已在 v0.9 / v0.10 落地，剩下「建仓库 + `.gitignore`」尚未做。
>
> **判断当前成熟度的最简方法**：让一位**非开发人员**在院内测试机上把系统装起来。
> 装不起来 = 还是原型；装起来了但答错数 = 产品但不可信；两者都过 = 才是可交付。
