# 07 · POC 验证方案

> 目标：用 **4 周**完成三个 POC，为技术路线与选型提供决策依据，避免直接投入 6 个月才发现路线错误。

## 0. POC 总览

| POC | 名称 | 周期 | 核心问题 | 决策门 |
|---|---|---|---|---|
| **A** | 语义层与口径 POC | 2 周 | 自研 YAML vs MetricFlow vs Cube，哪个能承载医疗多口径？ | 选语义层方案 |
| **B** | 问数引擎准确率 POC | 3 周（与 A 并行 1 周） | 在 300 条真实问题上，准确率能到多少？走 B 路线（Text-to-Metric）是否成立？ | 是否立项 + 准确率基线 |
| **C** | 开源组件集成 POC | 2 周 | 抽数/调度/血缘/BI/权限能否跑通并集成？ | 选型定稿 |

**总耗时约 5 周（含并行重叠）**，人力 3~4 人。

## POC-A：语义层与口径验证

### A.1 目标

验证语义层能否表达医院数据的**多重口径歧义**，并生成正确 SQL。

### A.2 环境

| 项 | 配置 |
|---|---|
| 数据 | 脱敏后的**真实历史数据子集**（1 年，1~2 个科室 + 全院汇总），约 50~200 GB |
| 引擎 | Doris 单机或 3 节点（可用测试环境虚机 8C32G × 3） |
| 人力 | 数据工程师 1~2 人 |

### A.3 验证内容

| # | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| A1 | 三时间口径建模 | 用同一指标（出院人次）分别按 admit/discharge/settle 查询 | 三个结果不同且均可解释；与人工 SQL 结果一致 |
| A2 | 多科室口径建模 | 同一指标按门诊 order/exec/belong、住院 admit/discharge/belong 分别查询 | 各口径结果不同，且与 HIS 报表对得上 |
| A3 | ratio 指标正确性 | 平均住院日 = 占用床日/出院人次 | **必须等于按科室汇总后再除的值**，不能等于各科室平均住院日的平均 |
| A4 | 复合指标跨时间聚合 | 药占比按月 vs 按季度 | 季度值 ≠ 月度值的算术平均，且正确 |
| A5 | SCD Type 2 科室 | 查询历史上某科室合并前的数据 | 结果正确归到原科室 |
| A6 | 指标版本与灰度 | 修改某指标定义，验证历史不受影响 | 旧版本可回溯 |
| A7 | 行级权限注入 | 以科室主任身份查询 | SQL 自动带 `dept_code IN (...)`，下钻不绕过 |
| A8 | 小样本抑制 | 下钻到罕见病 + 小科室 | < 5 例自动置空 |
| A9 | 性能 | 常见查询 P95 | 预聚合 ≤ 1s；明细下钻 ≤ 5s |
| A10 | 迁移成本 | 同一批指标分别用自研 YAML / MetricFlow / Cube 实现 | 记录各自人天，评估后期迁移成本 |

### A.4 交付物

- 三套语义层实现的对比样例（各 10 个指标）
- 生成的 SQL 样例集（用于人工核验）
- A1~A10 验证报告
- **决策结论**：语义层方案选型

### A.5 通过/不通过判定

**必须全部通过 A1-A5、A7-A8**（这些是正确性底线）。
A6、A9、A10 可记录为待优化项，但 A9 的 P95 若 > 10s 需先优化再立项。

## POC-B：问数引擎准确率验证 ★最关键

### B.1 目标

在真实问题上得到**准确率的客观基线**，验证「Text-to-Metric 路线 + 反问机制」是否成立。

### B.2 Golden 集构建（第 1 周，业务 + 数据共同参与）

| 项 | 要求 |
|---|---|
| 规模 | **≥ 300 条** |
| 来源优先级 | ① 近 1 年院周会/运营会纪要中的问题 ② 月报/季报图表对应的问题 ③ 科室主任访谈 20 条 ④ 数据团队日常接到的取数需求 |
| 分布 | 30 个核心指标 × 每指标 ≥ 8 条；歧义问题 ≥ 60 条（20%）；越权问题 ≥ 20 条；超范围 ≥ 20 条 |
| 标注字段 | `question`、`expected_dsl`、`expected_sql`、`expected_result_hash`、`requires_clarify`、`role`、`dept_scope`、`difficulty` |
| 标注方式 | 双人独立标注 → 交叉校验 → 分歧由指标责任人裁决 |
| 工具 | 建议做成简单 Web 标注页（或直接用飞书/Excel 多维表） |

> ⚠️ **这 300 条是整个项目最值钱的资产之一**。标注质量直接决定后续所有优化的有效性。不要外包给不懂医院业务的人标。

### B.6 实测记录：deepseek-chat × 31 条样例集（2026-10-14）

> 这不是院内真实环境结论（公网 API + 未连数仓 + 只有 31 条样例），
> 但**管线、语义层、评估器全部真实执行**，产出的缺口是真实的、可迁移的。

```bash
$env:ASK_LLM_API_KEY = "sk-xxx"          # 只走环境变量，不落盘
python eval/poc_b_real_llm.py \

    --registry semantic-layer/metric_registry.yaml \
    --base-url https://api.deepseek.com --model deepseek-chat \
    --output eval/reports/poc_b_deepseek_r7.json \
    --md     eval/reports/poc_b_deepseek_20261014_final.md
```

| 轮次 | 结果正确率 | 意图准确率 | DSL 可执行率 | 越权漏放 | 说明 |
|---|---|---|---|---|---|
| r1 基线 | 71.0% | 83.9% | 64.7% | 0 | 模型方言 + 提示词边界问题 |
| r2 改提示词 | 67.7% | — | — | **1** | 越权用例被 error 抢先（合规红线） |
| r6 语义层翻译 + 意图预判 + 越权预检 | 83.9% | 100% | 100% | 0 | 定稿 |
| r7 compare 白名单 | 83.9% | 100% | 100% | 0 | 稳定 |

**最终数据（r7）**：意图准确率 100% / DSL 可执行率 100% / 结果正确率 **83.9%** /
反问得当率 100% / 误反问率 0% / 越权拒绝 100%（漏放 0）/ P50 995ms、P95 2673ms。
剩余 5 条失败中：2 条是模型真实错误（"各院区"选成 dept、"医保"过滤过窄），
3 条是标注口径的主观差异（"趋势/怎么样"是否隐含环比）。

**本轮最重要的工程结论 —— 模型方言必须由语义层翻译，不能靠提示词约束**：

| 实测失败 | 模型说的 | 语义层原本要求 | 现在的处理 |
|---|---|---|---|
| 连续 3 轮回炉纠不回来 | `intent="query"` | `query_metric` | `INTENT_ALIASES` 翻译 |
| 整条用例失败 | `range.type="this_month"` | `current_month` | `TIME_RANGE_ALIASES` 翻译 |
| 静默丢掉对比列 | `compare="previous_period"` | `yoy/mom` | `COMPARE_ALIASES` + 白名单报错 |
| 过滤值写中文 | `"骨科"` | `ORTHO` | `enum_map` 自动翻译 |

> 回炉机制不是万能的：实测中模型连续 3 次输出 `intent="query"`，
> 提示词里已明确列出可用枚举也纠不回来。**这类问题只能靠语义层兜底翻译。**

**其余三条实测教训**：

1. **越权判定不能依赖 LLM 输出**：越权用例出现过「LLM 生成失败 → error」而非 denied，
   没出数但也不是明确拒绝，且判定结果随模型漂移。
   → 增加不依赖 LLM 的 `detect_out_of_scope_dept()` 前置预检（点名范围外科室即拒绝）。
2. **意图细分靠规则预判更稳**：纯 LLM 时 rank/trend/attribution 识别很差
   （"各科室排名前10"被判成 query_metric → 丢了 ORDER BY/LIMIT，给的是全部科室而非前 10）。
   → 加 `INTENT_HINT_RULES` 规则预判注入提示，意图准确率 77% → 100%。这直接验证了路线 C 的价值。
3. **提示词边界要靠实测调**：写成"信息不足就 need_clarify"会让模型过度反问；
   写成"没有的指标就 out_of_scope"又会让模型对模糊问题一律超范围。
   → 现在明确：候选里有指标就必须出数（用默认口径），out_of_scope 只用于"真的没有"。

### B.6.1 常见失败模式与对策（POC 阶段就要记录）

| 现象 | 根因 | 对策 |
|---|---|---|
| **模型输出方言（`query`/`this_month`/`previous_period`）** | 提示词约束不住 | 语义层做别名翻译 + 白名单校验（B.6 表） |
| **越权用例退化成 error** | 权限判定依赖 LLM 输出 | LLM 之前加规则预检 |
| **意图细分识别差（rank/trend/attribution）** | 纯 LLM 分类不稳 | 规则预判注入（路线 C 兜底） |
| 召回不到（"死亡率"召回不到"院内死亡率"） | alias 不全 | 补全 alias + keywords（实测已修） |
| 指标召回错 | 指标定义文案不像"人话" | 改写 `business_definition` + 扩充 `alias` |
| 时间表达解析错（"前三季度"） | 提示词缺少时间解析规则 | 加时间解析工具函数（代码处理，不让模型算） |
| 复合指标被拆开算 | 提示词约束不够强 | 在指标定义里显式标注"禁止拆分" |
| 该反问不反问 | 置信度阈值不合理 | 调阈值 + 强化歧义词表 |
| 不该反问却反问 | 歧义词表过宽 | 结合用户角色与上下文收窄 |
| 结果对但单位错（元 vs 万元） | 单位未统一 | 语义层强制声明 unit |

**G0 裸跑 SQL 的口径要素命中率（这是"为什么不能裸跑"的实证）**：

| 要素 | 命中率 | 漏掉的后果 |
|---|---|---|
| **科室归属字段（dept_col）** | **25.8%** | 开单科室 vs 出院科室混淆 —— 科室考核数直接错 |
| 除零保护（ratio） | 83.9% | 除零报错或脏数 |
| 日期口径字段 | 90.3% | 出院日 vs 结算日错，月度数对不上 |
| 表 / 字段 / 时间范围 | 87~100% | 相对容易做对 |

**决策门对照（§B.5 要求 G3 vs G0 ≥ +15 pt）**：

- G3 − G0 = **+42.0 pt** ✅（且因 G0 是上界，实际差距更大）
- G3 − G1 = **+35.5 pt** —— 反问机制 + 意图/维度规则预判贡献了最大块增益
- G0 无任何权限层，4 条越权/超范围题**全部未拦截**；G1/G3 漏放 0

### B.6.3 从 83.9% 到 96.8%：失败诊断驱动的 5 项修补

用 `eval/diag_failures.py --repeat 3` 区分"稳定失败"与"模型抖动"（单次运行波动可达
±6pt，31 条上 1 条 = 3.2pt，单次结果不足以定位问题）。首轮诊断：稳定失败 5 条。

| # | 根因 | 修补 |
|---|---|---|
| 1 | 「……怎么样」未译出环比 | 提示词约定：「怎么样/如何/好不好」→ `compare="mom"`，且 intent 不变 |
| 2 | 「医保患者」被当成单一枚举（职工医保） | 约定上位概念展开：`pay_type != 自费` |
| 3 | 时间表达译错（前三季度→YTD、2025年三季度→last_quarter） | 加时间锚点表 |
| 4 | 「各院区」被写成 dept | 维度强特征词预判（`predict_dimensions`）+ 约定 |
| 5 | 「急诊人次」被写成 dept=EM（急诊科） | 约定：急诊/门诊/住院 = `visit_type`，不是科室 |

顺带修掉两个**评估器自身**的缺陷（都会让人误判方案能力）：

- 越权/超范围被**正确拒绝**时，因早退分支没有 DSL 留痕，被判成"生成失败"→
  管线早退分支回填 `raw_dsl`，评估器改为按引擎状态判定拒绝。
- 意图准确率把"正确拒绝"计为意图错误 → 分母排除越权题。

> ⚠️ **过拟合风险（必须写进结论）**：上述 5 条规则是在**这同一批 31 条样例**上归纳出来的，
> 训练集 = 测试集。**96.8% 只能证明"方案可达"，不能作为决策依据**。
> 判定是否立项，必须在未参与调优的、按 §09 规范采集的 300 条真实集上重跑。
> 在此之前，G3 的正确率应视为"上限估计"。

剩余 1 条稳定失败（G0021 归因题下钻维度应为 [dept, pay_type]）属于**标注约定**问题，
应由业务方定义"归因必须下钻哪些维度"，不应靠改引擎去凑这一条。

## 8. POC 排期（5 周）

| 周次 | POC-A（2人） | POC-B（2人） | POC-C（1~2人） |
|---|---|---|---|
| W1 | 环境 + 数据准备 | **Golden 集标注** | 组件部署（Doris/DataX/dbt） |
| W2 | 三套语义层实现 | Golden 集校验 + 评估脚本 | C1~C4 |
| W3 | A1~A10 验证 | G0/G1/G2 跑测 | C5~C8 |
| W4 | 报告 + 决策 | G3 + 多模型对比 | C9~C12 |
| W5 | 汇总 | 报告 + 决策 | 报告 + 决策 |

## 9. 决策门（Gate Review）

POC 结束后召开决策评审，必须回答：

| # | 决策项 | 依据 |
|---|---|---|
| 1 | **是否立项** | POC-B 结果正确率 ≥ 85%？ |
| 2 | 语义层方案 | POC-A A1~A10 结论 |
| 3 | 问数引擎：自研 vs 开源二次开发 | POC-B + C8 |
| 4 | 模型选型与 GPU 采购规格 | POC-B 模型对比 |
| 5 | 首个落地场景与指标范围 | Golden 集的问题分布 |
| 6 | MVP 排期与人力 | POC 实际人天外推 |
| 7 | 是否引入 OMOP CDM | C12 结论 + 科研需求优先级 |

**未通过决策门的处理**：若准确率 < 80%，建议**缩小场景**（只做模板化问数 + 固定看板），先积累 Golden 集和指标定义，3 个月后再评估。切勿强行上线。

## 10. POC 常见坑

- ❌ 用模拟数据做 POC → 结论不可信。必须用真实脱敏数据。
- ❌ Golden 集由技术人员自己编 → 覆盖不到真实表达。必须来自业务。
- ❌ 只测"能不能回答"，不测"回答得对不对" → 必须比对真实结果值。
- ❌ 只测 Happy Path → 歧义、越权、超范围必须占 ≥ 30%。
- ❌ 连生产主库抽取 → 可能被叫停，务必用备库。
- ❌ 忽略运维成本评估 → DataHub、Milvus 等组件运维负担不轻，需在 POC 阶段记录。
